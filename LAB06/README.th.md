# LAB06 — Agentic AI System: ช่วยด้วย (ChuayDuay) (งานทีม)

[English](README.md) · ภาษาไทย

**repo ของทีม: [pitchakorn-pkt/chuayduay](https://github.com/pitchakorn-pkt/chuayduay)**

ช่วยด้วย (ChuayDuay) คือผู้ช่วยตอบคำถามภาษาไทยเรื่องปัญหาการใช้งานมือถือและคอมพิวเตอร์
ทำเป็นทีม 8 คน ในงาน DL-06 *Agentic AI System I* ตัวระบบเป็น agentic RAG ที่แยกเป็น
8 service คุยกันผ่าน HTTP โดยมี router ตัดสินใจทีละคำถามว่าจะตอบจากคลังความรู้ของเราเอง
พร้อมแหล่งอ้างอิง ตอบด้วย LLM ทั่วไป ใช้โมเดลจำแนกที่เทรนเองในเครื่อง ถามผู้ใช้กลับ
หรือปฏิเสธ ทั้งระบบขึ้นได้ด้วยคำสั่ง `docker compose` คำสั่งเดียว

**ส่วนของผม: หัวหน้าทีม และโมดูล 08 — Docker / Integration** สมาชิกอีก 7 คนรับผิดชอบคนละ
1 service ส่วนผมดูแลทุกอย่างที่เชื่อม service เหล่านั้นเข้าด้วยกัน ได้แก่ repo และกติกา
การทำงาน สัญญา API ที่ทุก service เขียนโค้ดตาม การตั้งค่า Docker การทดสอบและวัดผลทั้งระบบ
การรีวิวและ merge ทุก Pull Request และเซิร์ฟเวอร์ Discord ที่ทีมใช้ทำงาน
รายละเอียดของตัวระบบและผลที่วัดได้อยู่ใน README ของทีม ([`README.md`](README.md)
ใต้เส้นคั่น ซึ่งเป็นภาษาไทยอยู่แล้ว) ส่วนหน้านี้อธิบายว่าผมทำอะไรไปบ้าง

## สิ่งที่ผมทำ

### 1. ตั้งโปรเจกต์ให้ 8 คนเริ่มงานได้ตั้งแต่วันแรก โดยไม่ต้องรอกัน

การให้ 8 คนสร้าง 8 service ไปพร้อมกันจะเป็นไปได้ก็ต่อเมื่อไม่มีใครต้องรอ service ที่อยู่ก่อนหน้า
วันแรก (16 ก.ย.) ผมจึงวางของ 3 อย่างไว้ก่อนที่ใครจะเริ่มเขียนฟีเจอร์

- **สัญญา API** — [`docs/CONTRACT.md`](docs/CONTRACT.md) กำหนดรูปแบบ JSON ของทุกการเรียก
  ระหว่าง service และชื่อตัวแปร env ทุกตัว ถ้าโค้ดขัดกับสัญญา ถือว่าโค้ดผิด สัญญานี้ขึ้นไปถึง
  v1.7 ตอนจบงาน ทุกครั้งที่แก้ต้องผ่าน Pull Request และมีแจ้งเตือนเข้า Discord
- **โครงของทั้ง 8 service ที่รันได้จริง** — ทุก service มีตัว stub ที่ตอบกลับตามรูปแบบของสัญญา
  อยู่แล้ว และ `api` กับ `router` เรียก service ถัดไปผ่าน HTTP จริง ตั้งแต่ชั่วโมงแรก
  ทุกคนจึงรันทั้งระบบได้ เอาโค้ดจริงของตัวเองไปแทน stub แล้วเห็นผลตลอดทั้งเส้น
  โดยไม่มีใครต้องเขียน mock ของ service คนอื่นเอง
- **ข้อมูล** — คลังความรู้ (`daily_tech_qa.txt` คู่ถาม–ตอบ 10 หมวด) และ golden set
  60 คำถามพร้อมเฉลย มาจาก [`LAB04`](../LAB04/) ของผมเอง การส่งให้ตั้งแต่วันแรกทำให้โมดูล
  retrieval สร้างและวัดผลได้ทันที ไม่ต้องรอหาชุดข้อมูล

กติกาของ repo มาจากข้อกำหนดข้อเดียวของงานนี้ คือส่วนร่วมของทุกคนต้องมองเห็นได้
**คนละหนึ่งโฟลเดอร์ คนละหนึ่ง branch** — แต่ละคนแก้ได้เฉพาะ `services/<โฟลเดอร์ของตัวเอง>/`
บน branch `feature/…` ของตัวเอง เข้า `develop` ได้ทาง Pull Request เท่านั้น และ `main`
รับ merge จาก `develop` อย่างเดียว เจอบั๊กใน service ของคนอื่นให้เปิด Issue แท็กเจ้าของ
ไม่แก้แทนกัน ประวัติ commit จึงบอกได้ตรง ๆ ว่าใครทำอะไร branch protection บังคับให้ต้องผ่านการรีวิว
และ `.github/CODEOWNERS` ผูกแต่ละโฟลเดอร์กับเจ้าของไว้ GitHub จึงขอรีวิวจากคนที่ถูกต้องให้เองทุก PR

### 2. จัดงานให้ทุกคนรู้ชัดว่าต้องทำอะไร

- **ใบงานของแต่ละโมดูล** โพสต์และปักหมุดไว้ในห้อง Discord ของเจ้าของโมดูล บอกว่าโมดูลนั้น
  รับผิดชอบอะไร โฟลเดอร์และ branch ไหนเป็นของตัวเอง ตามสัญญาแล้วรับอะไรเข้าและส่งอะไรออก
  และโมดูลไหนรอโมดูลนี้อยู่ พอพบว่าใบงานชุดแรกขัดกับโครงที่วางไว้แล้ว (ยังสั่งให้สร้างของที่มีอยู่แล้ว)
  ผมเขียนใหม่ทั้ง 7 ใบแล้วปักหมุดใหม่ในวันที่สอง
- **เอกสารกลาง** ใน [`docs/`](docs/) ได้แก่ ภาพรวมแผน ตารางเวลา (ใครส่งอะไรวันไหน ใครรอใคร)
  และคู่มือ git ที่เขียนสำหรับคนที่ไม่เคยใช้ git มาก่อน
- **เซิร์ฟเวอร์ Discord ที่สร้างด้วยสคริปต์ ไม่ได้กดทีละอย่าง** ผมเขียนบอท (`setup_discord.py`
  เก็บไว้นอก repo นี้เพราะมี token ของบอท) ที่อ่าน `config.yaml` ไฟล์เดียวแล้วสร้างให้ครบ
  ได้แก่ role 9 อัน (หัวหน้า และอีกหนึ่งอันต่อโมดูล พิมพ์ `@retrieval` ก็ถึงตัวคนที่ถูกต้อง)
  ห้อง 18 ห้องใน 3 หมวด คือส่วนกลาง ห้องของแต่ละโมดูล และห้องสำหรับงานที่ข้ามโมดูล รวมทั้ง
  webhook และใบงานที่ปักหมุดในแต่ละห้อง สคริปต์รันซ้ำได้ (idempotent) แก้ config แล้วรันใหม่
  ได้โดยไม่สร้างของซ้ำ
- **แจ้งเตือนจาก GitHub เข้า Discord** ([`.github/workflows/`](.github/workflows/))
  workflow แรกโพสต์เมื่อมีการเปิด merge หรือปิด Pull Request และแท็กเจ้าของโมดูล อีกตัวเตือน
  ทันทีเมื่อมีใครแตะ `CONTRACT.md` เพราะเป็นไฟล์เดียวที่ถ้าพังจะกระทบทั้ง 8 คนพร้อมกัน

### 3. โมดูล 08 — Docker และการรวมระบบ

| ไฟล์ | |
|---|---|
| `docker-compose.yml` | ทุก service, PostgreSQL, health check และ named volume สำหรับโมเดลกับดัชนีค้นหา image จึงเล็กและไม่ต้องโหลดใหม่ทุกครั้งที่ build |
| `docker-compose.override.yml` | โหมดพัฒนา แก้โค้ดใน `app/` แล้วเห็นผลภายใน 2–4 วินาทีโดยไม่ต้อง build ใหม่ ใช้บน Windows ได้ด้วย |
| `Makefile` | `make up / ps / logs / smoke / warmup / ingest / eval / backup` งานละหนึ่งคำสั่ง และเขียนคำสั่ง `docker compose` เต็มไว้ในเอกสารสำหรับเครื่องที่ไม่มี `make` |
| `scripts/smoke_test.sh` | ตรวจ 14 ข้อตลอดทั้งเส้น ได้แก่ `/health` ของทุก service, ล็อกอิน, คำถามหนึ่งข้อต่อหนึ่ง route (ครบ 5), ประวัติ และสถิติ |
| `scripts/eval_e2e.py`, `eval/golden.jsonl` | ชุดวัดผลทั้งระบบ 64 คำถาม เรียกผ่าน `/api/chat` เหมือนผู้ใช้จริง เขียนผลเป็น `eval/report.md` และ `eval/report.html` ที่เปิดได้ในไฟล์เดียว |
| `08_monitoring_deployment/README.md` | คำสั่งที่ใช้ประจำ วิธีไล่หาจุดพังตอนรวมงานด้วย `request_id` เดียวผ่านทุก hop และหัวข้อสำหรับสมาชิกที่ใช้ Windows |

ทุก request มี `X-Request-ID` ส่งต่อไปทุก hop และทุก service log เป็น JSON บรรทัดเดียวต่อหนึ่งเหตุการณ์
คำถามว่า "service ไหนพัง" จึงตอบได้ด้วย `make logs` คำสั่งเดียว

### 4. รีวิวและ merge ทุก Pull Request

จาก Pull Request ทั้งหมด 35 อันใน repo มี 19 อันที่มาจากสมาชิกอีก 7 คน ผมรีวิวโดยเทียบกับสัญญา
และรัน branch นั้นจริงบนระบบอีกชุดที่แยกไว้ต่างหาก รวมแล้ว **approve 19 ครั้ง และขอให้แก้ 5 ครั้ง**
และ merge เอง 14 อัน (ที่เหลือเจ้าของ merge เอง) เมื่องานแก้ของสมาชิกพร้อมแล้วแต่ยังไม่ได้เปิด
Pull Request ในช่วงใกล้วันนำเสนอ ผมเปิด Pull Request ให้โดยคง commit และชื่อผู้เขียนเดิมไว้ครบ
(#19 โมดูล 06)

การรีวิวที่ได้ผลมากที่สุดไม่ใช่การอ่าน diff วันที่ 20 ก.ย. ผมส่งข้อความแปลก ๆ เข้า `/api/chat`
แบบที่ผู้ใช้จริงจะพิมพ์ ทั้งพิมพ์ผิด ไทยปนอังกฤษ คำถามต่อเนื่อง การพยายาม jailbreak และคำสั่ง
ที่ซ่อนอยู่ในไฟล์แนบ แล้วแจ้งผลแต่ละข้อให้เจ้าของโมดูล ข้อที่ร้ายแรงที่สุดคือ prompt injection
ผ่านเนื้อไฟล์ในโมดูล 04 ข้ออื่น ๆ ได้แก่ เส้น RAG ตันเมื่อคำตอบไม่อยู่ในคลัง (03) คำทักทายโดนถามกลับ (03)
และเลขอ้างอิงรูปแบบ `[1, 2, 3]` หายไป (06) ปัญหาของ router และ injection เจ้าของแก้แล้วใน
#22 และ #25 และกฎของเส้น RAG เขียนเข้าสัญญาเป็น v1.7 (#24)
