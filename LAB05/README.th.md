# LAB05 — รวมปัญหาของทุกระบบที่พัฒนาขึ้นในวิชานี้

[English](README.md) · ภาษาไทย

ในวิชานี้มีสามแล็บที่สร้างระบบที่ทำงานได้จริง คือ data pipeline ของงานทีมใน
[`LAB01/`](../LAB01/) ระบบค้นคืนคำถาม-คำตอบอาหารไทยใน [`LAB02/`](../LAB02/)
และระบบถาม-ตอบภาษาไทยเรื่องปัญหามือถือและคอมพิวเตอร์ใน [`LAB04/`](../LAB04/)
แต่ละระบบมีโฟลเดอร์ `problems/` ที่เขียนไว้ระหว่างพัฒนา แล็บนี้คือการรวมทั้งสามชุด
มาไว้ที่เดียวกัน รวม **21 ปัญหา** พร้อมสาเหตุ วิธีตรวจ และการแก้ที่ทำไปแล้ว
หรือเหตุผลที่ยังไม่แก้

ทุกอย่างใน [`problems/`](problems/) เป็นสำเนาของคำอธิบายที่อยู่คู่กับระบบต้นทาง
ต้นฉบับยังอยู่ที่เดิม เพราะปัญหาควรอยู่ข้างโค้ดที่มันพูดถึง สิ่งที่โฟลเดอร์นี้เพิ่มเข้ามา
คือการได้เห็นทั้งสามระบบพร้อมกัน ซึ่งเป็นจุดที่ความซ้ำเริ่มโผล่ออกมา

## วิธีรัน

ทุกปัญหามีสคริปต์ที่ทำซ้ำให้เห็นได้จากไฟล์ที่ commit ไว้ในรีโปนี้อยู่แล้ว
เริ่มจาก clone เปล่า

```bash
cd LAB05
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cd problems
python main.py                     # เมนู
python main.py lab04               # ทั้งชุด — เก้าข้อของ LAB04
python main.py lab04 6             # ข้อเดียว
python main.py 0                   # ทั้งหมด 21 ข้อ
```

แต่ละชุดยังรันแยกจากในโฟลเดอร์ของตัวเองได้เหมือนตอนอยู่แล็บต้นทาง —
`cd problems/lab02 && python main.py 0`

มีสองเรื่องที่ต้องรู้ สคริปต์อ่านผลลัพธ์แต่ละขั้น ดัชนี และไฟล์ต้นทางที่อยู่ใต้
`LAB01/` `LAB02/` และ `LAB04/` ไม่ได้พกสำเนาข้อมูลมาด้วย ดังนั้นสามโฟลเดอร์นั้น
ต้องมีอยู่ และมีหกข้อจาก 21 ข้อที่โหลดโมเดล embedding — LAB01 ข้อ 3 กับ LAB02
ข้อ 1 ถึง 5 ซึ่งจะดาวน์โหลด `paraphrase-multilingual-MiniLM-L12-v2` ในการรัน
ครั้งแรก อีกสิบห้าข้อที่เหลือรวมทั้งเก้าข้อของ LAB04 อ่านไฟล์ที่ commit ไว้
แล้วรันฟังก์ชันจริงทับลงไป

## สิ่งที่เห็นเมื่อเอามารวมกัน

พอวางเรียงข้างกัน ปัญหาเดิมโผล่ซ้ำในระบบที่สร้างห่างกันเป็นเดือน คนละเทมเพลต
คนละคลังข้อมูล

**การแบ่ง chunk ที่ไม่เคยทำงาน** LAB02 ข้อ 1 กับ LAB04 ข้อ 4 คือข้อค้นพบเดียวกัน
record เข้าเท่ากับ chunk ออก เพราะทุก record สั้นกว่า `CHUNK_SIZE` อยู่แล้ว
ส่วน LAB01 ข้อ 3 คืออีกครึ่งหนึ่งของเรื่องเดียวกัน — เพดานความยาวเขียนเป็นตัวอักษร
ขณะที่โมเดลนับเป็นโทเคน เพดานที่ดูปลอดภัยจึงปล่อยให้ 163 จาก 518 chunk ถูกตัดทิ้ง
สามระบบ นิสัยเดียว คือค่าความยาวที่เขียนด้วยหน่วยที่โมเดลไม่ได้ใช้ และไม่มีการตรวจ
ว่าขั้นตอนนั้นได้ทำอะไรลงไปจริงไหม

**metadata ที่เขียนไว้แล้วไม่มีใครอ่าน** LAB02 ข้อ 2 กับ LAB04 ข้อ 5 ต่างก็ติด
หมวดหมู่ให้ทุก chunk แล้วไม่เคยเรียกใช้บนเส้นทางค้นหาเลย ใน LAB02 ความเสียหาย
วัดออกมาได้ คือ 47 จาก 90 chunk มีเพื่อนบ้านใกล้สุดอยู่คนละเมนู

**การวัดผลที่มาทีหลัง แล้วพอมาก็ตันเพดาน** LAB02 ข้อ 6 ไม่มีชุดวัดผลเลย ส่วน
LAB04 ข้อ 9 มีแต่คำถามลอกมาจากคลังตรง ๆ สี่ใน variant ห้าแบบจึงได้ 1.0000
เท่ากันหมดและแยกอะไรไม่ออก ชุดทดสอบที่สอบตกไม่ได้เลยคือจุดบอดเดียวกับการไม่มี
ชุดทดสอบ แค่เดินมาจากคนละทาง

**ตอบทั้งที่ไม่มีอะไรให้ตอบ** LAB02 ข้อ 5 กับ LAB04 ข้อ 1 คือเกณฑ์ตัดที่ขาดหายไป
เหมือนกัน ทั้งสองระบบมีช่องว่างของคะแนนระหว่างคำถามในคลังกับนอกคลังอยู่ในตัวเลข
อยู่แล้ว เพียงแต่ไม่มีใครอ่านมัน

**ส่วนใหญ่ไม่มี error ให้เห็น** จาก 21 ข้อ ข้อที่จับได้เร็วล้วนจับได้เพราะมีอะไร
สักอย่างคอยรายงานออกมาดัง ๆ ว่ามันทำอะไรลงไป — ชุด boilerplate ที่เขียนลงไฟล์ทุกรอบ
จำนวนที่ถูกตัดที่พิมพ์เป็นคำเตือน และการตรวจป้ายอ้างอิงที่รันกับทุกคำตอบ
นั่นคือแบบแผนที่ควรเอาไปใช้ต่อในโปรเจกต์จบ

อีกหนึ่งความซ้ำที่ไม่ใช่ข้อบกพร่องของการออกแบบ LAB01 ข้อ 5 กับ LAB04 ข้อ 8 คือ
ชื่อโมเดลของ Groq ที่ถูกถอดออกตัวเดียวกัน โดนมาแล้วสองระบบ

## สิ่งที่แล็บนี้ยังพิสูจน์ไม่ได้

ที่นี่ไม่ได้วัดอะไรใหม่เลย ตัวเลขทุกตัวบนหน้านี้คือตัวเลขที่วัดไว้ในแล็บของมันเอง
บนข้อมูลของแล็บนั้น และทำซ้ำได้ด้วยสคริปต์ตัวเดิม สิ่งที่โฟลเดอร์นี้เพิ่มคือมุมมอง
ที่อ่านข้ามระบบ ไม่ใช่หลักฐานชุดใหม่

ทั้งสามชุดเป็นสำเนา ถ้าคำอธิบายต้นทางใน `LAB01/problems/` `LAB02/problems/`
หรือ `LAB04/problems/` ถูกแก้ สำเนาที่นี่จะไม่ตามไปเอง

และ 21 ปัญหาจากสามระบบที่นักศึกษาคนเดียวสร้างในหนึ่งเทอม ไม่ใช่การสำรวจอะไรทั้งนั้น
ความซ้ำข้างบนควรถูกอ่านอย่างจริงจังในฐานะนิสัยของคนที่เขียนมันขึ้นมา ซึ่งเป็นจุดประสงค์
ของแบบฝึกหัดนี้ ไม่ใช่ข้อสรุปเกี่ยวกับระบบ RAG โดยทั่วไป
