## 0. สิ่งที่อาจารย์ยืนยันมาแล้ว — อ่านก่อนอย่างอื่น

ถามอาจารย์ตรง ๆ เรื่องขอบเขต ได้คำตอบกลับมาว่า

> **"ไม่จำเป็นครับ ปรับได้ทั้งหมด ขอแค่ให้ระบบมันเท่ และทุกคนต้องมีส่วนร่วม"**

แปลเป็นข้อปฏิบัติได้สามข้อ

**1. โดเมนของข้อมูลปลดล็อกแล้ว** ไม่ต้องเป็นเอกสารมหาวิทยาลัย ไม่ต้องเป็นระเบียบ/ประกาศ
เราจึงใช้ **คลังปัญหาการใช้งานมือถือและคอมพิวเตอร์ในชีวิตประจำวัน** ที่มีอยู่แล้ว 194 คู่ถาม-ตอบ พร้อม golden set 60 ข้อ
ข้อดีที่ไม่ใช่แค่ความสะดวก: คนดูเข้าใจคำถามทันทีโดยไม่ต้องอธิบายบริบท และเรามีชุดวัดผลตั้งแต่วันแรก

**2. สถาปัตยกรรมปรับได้** แต่เราจะ **ไม่ปรับโครง 8 โมดูล** เพราะมันคือกรอบที่อาจารย์ใช้แบ่งงานและใช้ดูว่าใครทำอะไร
สิ่งที่เราปรับคือรายละเอียดภายใน (cascade router, retrieval เฉพาะ route ที่ต้องใช้, passthrough ไม่เรียก LLM ซ้ำ) ซึ่งทำให้ระบบดีขึ้นโดยไม่ทำให้ผังเสีย

**3. "ทุกคนต้องมีส่วนร่วม" คือเกณฑ์ให้คะแนน ไม่ใช่คำพูดลอย ๆ**
และการมีส่วนร่วมต้อง **พิสูจน์ให้เห็นได้** ไม่ใช่แค่เกิดขึ้นจริง — ดูหัวข้อ 9

**4. "ระบบมันเท่" คือเกณฑ์อีกข้อ** และ "เท่" ในงานประเภทนี้ไม่ได้แปลว่าใส่ฟีเจอร์เยอะ แต่แปลว่า
- กด `make up` ครั้งเดียวแล้วทั้งระบบขึ้น
- ถามคนละแบบแล้วเห็นว่า **agent เลือกคนละทางจริง** พร้อมเหตุผล
- คำตอบมี **อ้างอิงที่กดแล้วไปถึงต้นทางได้**
- มี **ตัวเลขวัดผลจริง** ไม่ใช่ "มันตอบได้นะ"

## 1. ประเมินแผนของอาจารย์ (แบบตรงๆ)

แผนใน repo อาจารย์เป็น **guide ระดับ production** (SSO, Kafka, Prometheus, OpenTelemetry, Celery ฯลฯ) ถ้าทำตามทุกบรรทัดใน 1 สัปดาห์ด้วย 8 คน **จะไม่เสร็จ** และที่อันตรายกว่าคือจะได้ 8 ชิ้นที่ต่อกันไม่ติด
สิ่งที่ทำให้งานเราดีกว่าคือ "ตัดให้ถูก + เพิ่มจุดที่คนอื่นมองข้าม" ไม่ใช่ใส่ tool ให้เยอะที่สุด

### ระดับความสำคัญ (MoSCoW) ทั้งระบบ
- **Must (ไม่มี = สอบตก)**: ถามตอบได้ครบ 3 route หลัก + clarify/decline, RAG มี citation จริง, history + follow-up, feedback 👍👎, `docker compose up` คำสั่งเดียวรันได้

- **Could (ทำให้ "โหด")**: SSE streaming, reranker, Prometheus+Grafana, CI build อัตโนมัติ, HTTPS ผ่าน Caddy

## 2. สถาปัตยกรรมที่ใช้จริง

```
Browser ──> web (Next.js :3000) ──[server-side proxy]──> api (:8000)
                                                          │
                     ┌──── POST /route ───────────────────┤
                     ▼                                    │ POST /log (async, ไม่รอ)
                  router ──> engines   (/general, /local/classify)
                     │   ──> retrieval (/search)            ▼
                     │   ──> generation (/generate)     response-log ──> postgres
                     └── ตอบกลับ api                         ▲
                                                           │
api ──> postgres (users, uploaded_files)     api ──> response-log (/history, /feedback, /stats)
retrieval ──> volume: chroma index + bm25 index + hf model cache
```

ทำไม Router เป็นคนคุมลำดับ: มีจุดตัดสินใจจุดเดียว ถ้าจะเพิ่ม engine ใหม่แก้ที่ router ที่เดียว (ตรงกับ Design Rationale ของอาจารย์)

### ตาราง service
| โฟลเดอร์ | ชื่อใน compose | เจ้าของ | ภาษาหลัก | port ภายใน | เปิดออก host |
|---|---|---|---|---|---|
| `services/01_web_app` | `web` | คนที่ 1 | TypeScript (Next.js) | 3000 | 3000 |
| `services/02_api_backend` | `api` | คนที่ 2 | Python (FastAPI) | 8000 | 8000 |
| `services/03_ai_router_agent` | `router` | คนที่ 3 | Python (FastAPI) | 8000 | 8003 (debug) |
| `services/04_ai_model_selection` | `engines` | คนที่ 4 | Python (FastAPI) | 8000 | 8004 (debug) |
| `services/05_retrieval_knowledge` | `retrieval` | คนที่ 5 | Python (FastAPI) | 8000 | 8005 (debug) |
| `services/06_llm_generation` | `generation` | คนที่ 6 | Python (FastAPI) | 8000 | 8006 (debug) |
| `services/07_response_logging` | `response-log` | คนที่ 7 | Python (FastAPI) | 8000 | 8007 (debug) |
| `08_monitoring_deployment` + root | `postgres`, (`grafana`) | คนที่ 8 (หัวหน้า/เจ้าของ repo) | YAML, Dockerfile, Bash, Makefile | – | – |

ทุก container ฟัง port 8000 ภายใน (ยกเว้น web) คุยกันด้วยชื่อ เช่น `http://router:8000` **ห้ามใช้ localhost ระหว่าง service**


## 5. เรื่องภาษา — "หลัก" กับ "flex ได้"
ภาษาหลักตามตารางข้างบนคือค่าเริ่มต้น เลือกเพราะทีมจะช่วยกันอ่าน/แก้ได้ง่าย แต่ **ปรับได้** ตามความถนัด เงื่อนไขเดียวคือ
1. ยังตอบ/รับ JSON ตาม `CONTRACT.md` เป๊ะ
2. มี `GET /health`, อ่าน config จาก env, ฟัง port 8000
3. มี Dockerfile ที่ build ได้ (หัวหน้าช่วยทำให้ แต่ต้องบอกล่วงหน้าก่อน D2)
4. แจ้งในกลุ่มก่อนเปลี่ยน อย่าเปลี่ยนเงียบๆ

ตัวเลือก flex ที่สมเหตุสมผลเขียนไว้ในไฟล์ของแต่ละคน

## 6. LLM provider ที่ใช้ร่วมกัน — **Groq เป็นหลัก**

- **ตัวหลัก: Groq** (`LLM_PRIMARY=groq`) · ตัวสำรอง: Gemini หรือ OpenAI (`LLM_FALLBACK`)
- **ใช้ไลบรารี `openai` ตัวเดียวทั้งทีม** สลับเจ้าด้วยการเปลี่ยน `base_url` เท่านั้น ห้ามใครลง SDK เจ้าอื่นเพิ่ม
  ตาราง `base_url` ของทั้งสามเจ้าอยู่ใน `CONTRACT.md` §7 · รูปแบบนี้พิสูจน์แล้วว่าใช้ได้จริงจากงาน RAG เดิมของทีม
- โมเดลปัจจุบัน `GROQ_MODEL=openai/gpt-oss-120b` — **อ่านจาก env เสมอ ห้าม hardcode**
- key อยู่ใน `.env` ที่ root เท่านั้น ไม่ commit — แชร์ในกลุ่มแชทส่วนตัว

**สามเรื่องของ Groq ที่ต้องรู้ทั้งทีม**
1. **Groq ถอดโมเดลออกโดยไม่แจ้ง** ทีมเคยใช้ `llama-3.3-70b-versatile` แล้วโดนถอด (เจอเอง 18 ส.ค. 2026) → คนที่ 3, 4, 6 ต้องอ่านชื่อโมเดลจาก env และเช็กตอน startup
2. **free tier จำกัดคำขอต่อนาที** และเราแปดคน → **ตอน dev ทุกคนสมัคร key ของตัวเองฟรี** key กลางเก็บไว้ใช้วันสาธิตเท่านั้น · fallback provider ไม่ใช่ของประดับ ต้องทำจริงและทดสอบจริง
3. **Groq ไม่มีระบบ safety ฝั่งผู้ให้บริการแบบ Gemini** → ด่านความปลอดภัยทั้งหมดอยู่ที่คนที่ 6 คนเดียว ห้ามออกแบบโดยคิดว่าผู้ให้บริการกรองให้

**ข้อดีที่ควรใช้ประโยชน์**: Groq เร็วกว่าเจ้าอื่นมาก คอขวดของเราคือ rate limit ไม่ใช่ความเร็ว → งบเวลา 70 วินาทีของ router เหลือเฟือ เอาไปทำ reranking หรือ citation check เพิ่มได้

## 9. "ทุกคนต้องมีส่วนร่วม" — ทำให้พิสูจน์ได้

อาจารย์พูดข้อนี้ออกมาเอง แปลว่าท่านจะดู และในงานกลุ่ม 8 คนสิ่งที่มักเกิดคือ 2 คนทำ 6 คนดู
โครงที่วางไว้กันเรื่องนี้อยู่แล้วโดยบังเอิญ เหลือแค่ทำให้มัน**มองเห็นได้จากภายนอก**

**หลักฐานห้าอย่างที่ต้องมี ไม่ต้องทำอะไรเพิ่มนอกจากทำตามกติกาที่วางไว้**

| หลักฐาน | ได้มาจาก | ใครดูแล |
|---|---|---|
| หนึ่งคนหนึ่งโฟลเดอร์ หนึ่ง branch | `GIT_FLOW.md` + CODEOWNERS | 08 |
| **commit ของแต่ละคนกระจายตลอดสัปดาห์** ไม่ใช่ก้อนเดียววันสุดท้าย | `git shortlog -sn` + กราฟ contributors ของ GitHub | ทุกคน |
| PR เปิดโดยเจ้าของงานเอง ไม่ใช่หัวหน้า push ให้ | ประวัติ PR | 08 ห้าม push แทนใครเด็ดขาด |
| README ในโฟลเดอร์ตัวเอง พร้อม**ตัวเลขที่ตัวเองวัด** | DoD ของแต่ละคน | เจ้าของโฟลเดอร์ |
| แต่ละคน subtree งานตัวเองเข้า repo ส่วนตัว | `GIT_FLOW.md` | เจ้าของโฟลเดอร์ |

**ตอนนำเสนอ: ทุกคนพูดส่วนของตัวเอง คนละ 2 นาที** อย่าให้คนเดียวพูดหมด
คนที่ 8 เปิด `make up` และปิดท้ายด้วยตัวเลขจาก `eval/report.html` ส่วนคนที่ 1 สาธิตหน้าเว็บ
ให้แต่ละคนเตรียมตอบสามคำถามนี้เกี่ยวกับส่วนตัวเอง — **ซ้อมจริงในวัน D7**
1. ส่วนของคุณรับอะไรเข้า ส่งอะไรออก และคุยกับใคร
2. ปัญหาที่เจอคืออะไร แก้ยังไง
3. รู้ได้ยังไงว่ามันทำงานถูก (ตัวเลขหรือเทสต์อะไร)

**ถ้ามีคนส่งงานไม่ทัน** — ตัดสินใจที่ D5 ไม่ใช่ D6
โมดูลที่ยุบได้โดยระบบยังเดินคือ **07** (ย้ายไปรวมใน 02 ตามที่อาจารย์เขียนเองว่า "or embedded inside the API/Backend") และ **04 ฝั่ง local** (ปิด layer 2 ของ router แล้วข้ามไป layer 3)
**ห้ามยุบ 03 หรือ 05** ถ้าสองตัวนี้ไม่มา ระบบไม่เหลืออะไรให้สาธิต
ถ้าต้องยุบจริง ให้เจ้าของงานเดิมยังมีชื่อใน commit ที่เขาทำไว้ อย่าลบทิ้ง

## 10. สี่อย่างที่ทำให้ "เท่" โดยใช้เวลาน้อยที่สุด

เรียงตามคุ้มค่าต่อชั่วโมง ทั้งหมดใช้ข้อมูลที่ไหลอยู่ในระบบแล้ว ไม่ต้องเพิ่ม service

| | ทำอะไร | ใคร | เวลา | ทำไมถึงเท่ |
|---|---|---|---|---|
| 1 | **แผงแสดงการตัดสินใจของ agent** กดที่ badge แล้วกางเห็น `rules 3 ms → ค้นเอกสาร 340 ms → เขียนคำตอบ 1,520 ms` + เหตุผล | 01 (ข้อมูลจาก 03) | ~2 ชม. | เปลี่ยนจาก "แชทบอทอีกตัว" เป็น "เห็น agent คิด" ข้อมูลมีอยู่แล้วใน `trace` |
| 2 | **ปุ่มตัวอย่างคำถาม 5 ปุ่ม ปุ่มละ route** | 01 | ~15 นาที | ตอนสาธิตกดรัวให้เห็นว่าเลือกคนละทางจริง ไม่ต้องพิมพ์สด ไม่พลาด |
| 3 | **ตัวเลข "ไม่เรียก LLM กี่ %"** จาก `decided_at_layer` | 03 เก็บ, 07 สรุป, 08 ใส่รายงาน | ~1 ชม. | ตอบคำถาม "ทำไมไม่ถาม LLM ทุกครั้ง" ด้วยตัวเลขแทนความเห็น |
| 4 | **`eval/report.html`** หน้าเดียวจบ มีตารางเทียบ BM25 / vector / hybrid และ % citation ถูก | 08 | ~2 ชม. | ไม่มีใครถูกบังคับให้ทำ เพราะอาจารย์ไม่มี rubric — จึงเป็นจุดที่แยกเราออกจากกลุ่มอื่นชัดที่สุด |
