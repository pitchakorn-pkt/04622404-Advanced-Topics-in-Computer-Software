# LAB01 — ปัญหาของ data pipeline นี้ และสิ่งที่ทำกับมัน

[English](README.md) · ภาษาไทย

ปัญหาหกข้อที่พบใน LLM data pipeline ใน [`../`](../)
ครอบคลุมตั้งแต่ขั้นทำความสะอาดข้อมูลไปจนถึงคำตอบที่อ้างอิงแหล่งที่มา

หมายเหตุเรื่องที่มาของงาน — โฟลเดอร์นี้เป็นภาพรวมของ pipeline ที่ทำกันทั้งทีม
ขั้น Cleaning + Normalization และตัว embedding แบบรันในเครื่องเป็นส่วนของเจ้าของ repo นี้
ส่วน Collection, Chunking และ Metadata เป็นงานของเพื่อนร่วมทีม
ปัญหาข้อ 1, 2, 5 และ 6 อยู่ในขั้นที่เป็นงานของเจ้าของ
ข้อ 3 อยู่ *ระหว่าง* สองขั้นที่คนละคนดูแล ซึ่งเป็นที่อยู่ตามปกติของข้อบกพร่องประเภทนี้
และข้อ 4 เป็นคุณสมบัติของวิธีที่สองขั้นสุดท้ายต่อกัน

ตัวเลขทุกตัวในนี้วัดจากผลลัพธ์ของแต่ละขั้นที่ commit ไว้ แต่ละข้อมีสคริปต์ที่ทำซ้ำได้

## วิธีรัน

```bash
cd LAB01/problems
python main.py        # เมนู
python main.py 3      # ดูข้อเดียว
python main.py 0      # ทั้งหกข้อ
```

มีเฉพาะข้อ 3 ที่ต้องโหลดโมเดล ที่เหลืออ่านจากไฟล์ผลลัพธ์ที่ commit ไว้
แล้วรันฟังก์ชันทำความสะอาดตัวจริงซ้ำบนมัน
ส่วนข้อ 4 กับ 6 ดึงฟังก์ชันที่ต้องใช้ออกมาจาก `vector_store.py` โดยตรงแทนการ import ทั้งโมดูล
เพราะโมดูลนั้น import `chromadb` ซึ่งอยู่ใน `requirements.txt` แต่ไม่ได้ติดตั้งใน `.venv` ที่ใช้ร่วมกัน
ไม่ว่าทางไหน โค้ดที่ถูกรันก็เป็นโค้ดตัวจริง

## สิ่งที่ร้อยหกข้อนี้เข้าด้วยกัน

สี่ในหกข้อเป็นความล้มเหลวที่ไม่มี error ให้เห็น — ข้อความที่ถูกตัดด้วยกฎที่ถูกต้องในหลักการ
คลังหนึ่งในสามที่ถูกตัดทิ้งใต้เพดานที่ดูปลอดภัย provider ที่ไม่ตรงซึ่งแค่ทำให้คะแนนไร้ความหมาย
และป้ายอ้างอิงที่ถูกรูปแบบแต่ชี้ไปยังที่ที่ไม่มีอะไร

ส่วนสองข้อที่จับได้เร็ว จับได้เพราะมีอะไรบางอย่างถูกวางไว้ให้พูดออกมาดัง ๆ —
ชุด boilerplate ถูกเขียนลงไฟล์ทุกครั้งที่รัน จำนวนที่ถูกตัดถูกพิมพ์เป็นคำเตือน
และการตรวจป้ายที่แต่งขึ้นทำงานกับทุกคำตอบ
นี่คือรูปแบบที่ควรรักษาไว้ — ใน pipeline ที่ทุกขั้นถอยกลับอย่างนุ่มนวลได้
สิ่งเดียวที่ป้องกันได้คือขั้นที่รายงานว่าตัวเองทำอะไรไป
