# ปัญหาข้อ 03 — งบโทเคนถูกนับด้วยตัวนับหนึ่ง แต่ถูกใช้จ่ายด้วยอีกตัวหนึ่ง

[English](problem03_truncation.md) · ภาษาไทย · ทำซ้ำ: `python main.py 3`

## สิ่งที่ขั้น chunking เชื่อ

| | |
|---|---|
| chunk ทั้งหมด | 518 |
| ตัวนับที่ใช้ | tiktoken `cl100k_base` (`chunking.py:87-101`) |
| `token_count` ที่บันทึก | ต่ำสุด 50 · สูงสุด 500 · มัธยฐาน 397.5 |
| เกิน 512 ตามตัวนับนี้ | **0 จาก 518** |

ขั้นนี้ตั้งเพดานไว้ที่ 500 โทเคน ต่ำกว่า 512 ที่โมเดลรับได้
ตามตัวเลขของมันเองจึงไม่มี chunk ไหนยาวเกินเลย

## สิ่งที่โมเดลเห็นจริง

วัดด้วย tokenizer ของ `BAAI/bge-small-en-v1.5` เอง ซึ่ง `max_seq_length = 512`

| | |
|---|---|
| โทเคนต่อ chunk | ต่ำสุด 43 · สูงสุด 624 · มัธยฐาน 404 |
| เกิน 512 | **163 จาก 518 = 31.5%** |
| โทเคนที่หายไป | 2,955 |

ตัวนับสองตัวไม่ใช่ตัวเดียวกัน tiktoken คือ BPE ของ OpenAI ส่วน bge ใช้ WordPiece ของ BERT
ข้อความชิ้นเดียวกัน bge นับได้มากกว่า — chunk ที่แย่ที่สุดคือ 500 ตาม tiktoken
แต่ 624 ตาม bge ต่างกัน 124 โทเคน

งบจึงถูกตั้งในหน่วยหนึ่งและถูกใช้จ่ายในอีกหน่วยหนึ่ง
เพดาน 500 ที่ดูปลอดภัยจึงไม่ปลอดภัยจริง

และตัวเลขนี้ยังต่ำกว่าความจริง `embedding_text()` เติม header — ชื่อตำแหน่ง บริษัท สถานที่ —
เข้าไปก่อน embed ซึ่งกินงบก้อนเดียวกัน และไม่ถูกหักออกตอนกำหนดขนาด chunk
header อ่านจาก `retrieval_metadata` ที่ `04_metadata.py` เป็นคนเติม
และผลลัพธ์ของขั้นนั้น (`metadata_*.json`) ไม่ได้ถูก commit ไว้ จึงมี 0 จาก 518 chunk ที่มี header ให้วัด
การรันเต็มสายจริงจะถูกตัดมากกว่านี้

## อาการเวลาเกิดขึ้นจริง

sentence-transformers ตัดให้เงียบ ๆ โมเดลแค่หยุดอ่าน และเวกเตอร์ที่ได้ยังมีความกว้างถูกต้อง
ไม่มี error ไม่มีอะไรผิดสังเกต

ส่วนที่ถูกตัดคือส่วนที่จ่ายค่าประมวลผลไปแล้วในขั้น chunking และหายไปเลย
chunk นั้นจะค้นเจอได้ด้วยเนื้อหาส่วนต้นเท่านั้น แต่ยังถูกส่งให้ LLM เต็ม ๆ ตอนถูกใช้
สิ่งที่ค้นกับสิ่งที่อ่านจึงไม่ใช่ข้อความเดียวกันอีกต่อไป

## สิ่งที่มีอยู่แล้ว และสิ่งที่ยังขาด

`embedding.py:234-240` นับและเตือนไว้แล้วทุกครั้งที่รัน

```
WARNING: n/m texts are longer than 512 tokens and will be truncated
```

ซึ่งเป็นสิ่งที่ถูกต้อง — มันบอกออกมาดัง ๆ แทนที่จะปล่อยให้ไปเจอทีหลังในรูปของผลการค้นที่แย่ลงโดยไม่รู้สาเหตุ

ที่ยังขาดคือไม่มีอะไร **ป้องกัน** มัน คำเตือนมาถึงหลังจาก chunk ถูกสร้างและจ่ายค่าไปแล้ว
และไม่มีขั้นไหนอ่านคำเตือนนี้กลับไปปรับเพดาน

## สิ่งที่จะแก้ได้

ให้ขั้น chunking นับด้วย tokenizer ตัวเดียวกับที่ขั้น embedding จะใช้ แทนการใช้ tiktoken เป็นตัวแทน
แล้วหักความยาวของ header ออกจากงบด้วย

ถ้าไม่อยากผูกสองขั้นเข้าด้วยกัน ให้ลดเพดานลงเท่าส่วนต่างที่วัดได้
ซึ่งได้ผลกับคลังนี้ และต้องวัดใหม่ทุกครั้งที่เปลี่ยนโมเดล

## หมายเหตุเรื่องตัวเลขใน README ของแล็บ

README ของแล็บบันทึกว่า MiniLM ตัดเนื้อหา 72.7% ของ chunk เทียบกับ bge ที่ 2.6%
ซึ่งเป็นการวัดที่ใช้เลือก bge เมื่อ ก.ค. 2026
ตัวเลขวันนี้ไม่ตรงกับชุดนั้นแล้ว เพราะขั้น chunking เปลี่ยนไปหลังจากนั้น และไม่มีอะไรวัดซ้ำให้

นั่นคือปัญหาเดียวกับที่หน้านี้พูดถึง แต่สูงขึ้นไปอีกชั้น —
การวัดครั้งหนึ่งตัดสินการออกแบบ แล้วไม่มีอะไรตรวจการวัดนั้นซ้ำ

## ขั้นไหนเป็นงานของใคร

ขั้น chunking เป็นงานของเพื่อนร่วมทีม ส่วนขั้นทำความสะอาดและตัว embedding แบบรันในเครื่อง
เป็นส่วนของเจ้าของ repo นี้ ความไม่ตรงกันนี้อยู่ระหว่างสองขั้น ไม่ได้อยู่ในขั้นไหนขั้นหนึ่ง
ซึ่งเป็นที่อยู่ตามปกติของข้อบกพร่องประเภทนี้
