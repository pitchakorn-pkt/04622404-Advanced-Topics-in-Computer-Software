# ปัญหาข้อ 07 — ส่งข้อความที่ถูกให้แล้ว คำตอบยังเพี้ยน

[English](problem07_generation.md) · ภาษาไทย · ทำซ้ำ: `python main.py 7`

## อาการ

จาก `outputs/eval_generation.json` คำถาม 20 ข้อ

| | |
|---|---|
| อัตราค้นเจอ chunk ที่ถูก | 0.9500 |
| คำตอบมีเลขอ้างอิง | 1.0000 |
| faithfulness | 0.7862 |
| **correctness** | **0.5957** |
| relevance | 0.6328 |

ขั้นค้นหาทำงานของมันสำเร็จ 95% และคำตอบทุกข้ออ้างอิงแหล่งที่มา
ส่วนที่เหลือหายไประหว่างการเขียนคำตอบ

มีหนึ่งเคสที่จับได้ว่าเขียนขัดกับสิ่งที่ตัวเองอ้างตรง ๆ

| | |
|---|---|
| chunk `[1]` ที่ส่งให้ | เครื่องจะหยุดจ่ายไฟเมื่อแบตเต็ม |
| คำตอบที่เขียนออกมา | แม้แบตเต็มแล้วเครื่องยังจ่ายไฟเข้าแบต |

คำตอบอ้าง `[1]` ถูกต้องตามรูปแบบ แล้วเขียนตรงข้ามกับมัน ถามซ้ำอีกครั้งไม่เกิดอาการเดิม
จึงไม่ใช่ปัญหาเป็นระบบ แต่แสดงว่าเลขอ้างอิงไม่รับประกันอะไรเลยว่าประโยคตรงกับแหล่งที่มา

## ปัญหาที่สอง — ตัววัดมองปัญหาแรกไม่เห็น

คะแนนคุณภาพทั้งสามตัวคือการนับคำซ้ำ

```
faithfulness = word_overlap(คำตอบ, context)        eval_generation.py:78
correctness  = word_overlap(คำตอบ, คำตอบเฉลย)      eval_generation.py:79
relevance    = word_overlap(คำถาม, คำตอบ)          eval_generation.py:80
```

มันวัดสัดส่วนคำที่ใช้ร่วมกัน ไม่ได้วัดว่าความหมายตรงกันไหม
คำตอบเรื่องแบตข้างบนใช้คำแทบทั้งหมดร่วมกับ chunk ที่มันขัดแย้งด้วย
มันจึงได้ faithfulness *สูง* ทั้งที่ไม่ซื่อตรงต่อแหล่งที่มา

`faithfulness = 0.7862` จึงต้องอ่านว่า "คำตอบใช้คำจาก context เป็นส่วนใหญ่"
ไม่ใช่ "คำตอบซื่อตรงต่อ context" ตัววัดถูกตั้งชื่อตามสิ่งที่มันไม่ได้วัด

## เครื่องมือที่สร้างไว้แล้วแต่ยังไม่ได้ต่อสาย

`JUDGE_PROMPT` (`prompt_templates.py:97`) เขียนเสร็จพร้อมใช้ — ให้ LLM ให้คะแนนคำตอบ 1-5
ตามเกณฑ์ที่ระบุ แล้วคืนเป็น JSON พร้อมเหตุผล

grep ทั้งโปรเจกต์แล้วไม่มีไฟล์ไหน import หรือเรียกใช้เลย ขั้นวัดผลจึงยังเป็นการนับคำล้วน

ที่ปล่อยไว้ไม่ต่อสายเป็นการตัดสินใจ เพราะการเปิดใช้จะได้ตัวเลขชุดใหม่ที่อาจขัดกับตัวเลข
ที่อยู่ใน `README.md` และในสไลด์นำเสนอไปแล้ว จึงเลือกที่จะไม่เปลี่ยนตัวเลขที่รายงานไว้ก่อนส่ง
นี่คือสิ่งแรกที่ควรทำถ้าจะต่อยอดระบบนี้

## ข้อที่ค้นเจอถูกแต่ faithfulness ต่ำที่สุด

| id | faithfulness | correctness | คำถาม |
|---|---|---|---|
| g0035 | 0.6757 | 0.5676 | สงสัยว่าเพื่อนบ้านมาเกาะสัญญาณของเรา ตรวจดูได้มั้ย |
| g0042 | 0.6809 | 0.5106 | อยากได้อะไรที่คนอื่นเดาไม่ออกแต่เราไม่ลืมเอง ควรตั้งแบบไหน |
| g0010 | 0.7273 | 0.6364 | เปิดโหมดถนอมพลังงานแล้วอยู่ได้นานขึ้นจริงหรือเปล่า ต้องแลกกับอะไร |

คำซ้ำน้อยไม่ได้พิสูจน์ว่าคำตอบผิด คำตอบที่ดีซึ่งเรียบเรียงด้วยคำของตัวเองก็ได้คะแนนต่ำเหมือนกัน
ความกำกวมตรงนี้แหละคือเหตุผลที่ต้องมี LLM มาเป็นผู้ตัดสิน

## สิ่งที่แก้ไปแล้วในขั้นนี้

**ธง `no_context` เป็น false เสมอ** เมื่อไหร่ที่มี chunk ธงนี้จะบอกว่าระบบตอบได้
ผู้เรียกจึงแยกไม่ออกระหว่างคำตอบกับการปฏิเสธ ตอนนี้มันดูจากว่ามีข้อความปฏิเสธของ LLM
ปรากฏอยู่ไหม (`generator.py:99-102`)

**กฎ prompt ข้อ 2 กับ 3 ขัดกันเอง** ข้อ 2 บอกให้ตอบด้วยข้อความปฏิเสธคำเดียวจบ
ส่วนข้อ 3 บอกให้ใส่ `[n]` ท้ายทุกประโยคที่ใช้ข้อมูล ผลคือได้คำตอบหน้าตา `ไม่พบข้อมูล [1][2][3]`
ตอนนี้กฎข้อ 2 ห้ามใส่เลขอ้างอิงไว้ชัดเจน (`prompt_templates.py:16`)

**`NoLLM` แยก prompt ด้วยคีย์ภาษาอังกฤษ** ทั้งที่ prompt เป็นภาษาไทย เส้นทางสำรองจึงคืนข้อความผิด
ตอนนี้ทั้งสองฝั่งใช้ค่าคงที่ตัวเดียวกัน (`prompt_templates.py:24-25`)

## วิธีตรวจสอบ

อ่าน `อัตราค้นเจอ chunk ที่ถูก` คู่กับ `correctness` อัตราค้นเจอสูงแต่ correctness ต่ำ
แปลว่าความผิดพลาดอยู่หลังขั้นค้นหา จากนั้นต้องอ่านคำตอบจริงเทียบกับ chunk ที่มันอ้าง
เพราะเมื่อตัววัดเป็นการนับคำซ้ำ การอ่านเองข้ามไม่ได้
