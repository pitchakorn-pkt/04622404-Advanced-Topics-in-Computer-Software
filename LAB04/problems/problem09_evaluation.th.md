# ปัญหาข้อ 09 — ตัววัดผลคือส่วนที่มีโอกาสโกหกมากที่สุด

[English](problem09_evaluation.md) · ภาษาไทย · ทำซ้ำ: `python main.py 9`

ตัวเลขทุกตัวที่อ้างในปัญหาอีกแปดข้อมาจากไฟล์เหล่านี้
ข้อนี้ถามว่าเชื่อถือมันได้ไหม และแสดงสี่ทางที่มันเกือบเชื่อไม่ได้

## 1. variant สี่ในห้าตัวตัดสินอะไรไม่ได้เลย

MRR แยกตาม variant ทั้งสี่คอนฟิก คำถาม 60 ข้อ

| variant | dense_only | bm25_only | hybrid | hybrid+rerank |
|---|---|---|---|---|
| verbatim | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| slang | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| partial | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| natural | 1.0000 | 1.0000 | 1.0000 | 1.0000 |
| **paraphrase** | **0.8961** | **0.4953** | **0.7219** | **0.9482** |

สี่แถวบนเท่ากันหมดทุกคอนฟิก รวมทั้ง `bm25_only` ที่อ่อนที่สุดแบบทิ้งห่าง
ถ้าอ่านแต่แถวพวกนี้จะสรุปว่า "ทุกคอนฟิกดีเท่ากัน" ซึ่งผิด

มันถูกสร้างจากคำถามในคลังโดยแก้เพียงเล็กน้อย เหลือคำซ้ำกับต้นฉบับ 1.00 / 1.00 / 0.99 / 0.86
การค้นจึงลดรูปเหลือแค่การจับคู่คำเดิมกลับ ส่วน `paraphrase` เขียนใหม่ด้วยมือทั้ง 60 ข้อ
จนเหลือคำซ้ำเฉลี่ย 25%

`paraphrase` เป็นแถวเดียวที่แยกอะไรออก และเป็นแถวเดียวที่ใช้รายงานทุกที่

**ชุดข้อสอบที่ทุกคอนฟิกได้เต็ม ไม่ได้แปลว่าระบบดี แปลว่าชุดข้อสอบวัดไม่ได้**

## 2. ตัววัดเคยข้ามขั้นที่ระบบจริงทำ

`main.py` เรียก `normalize_query()` ก่อนค้นทุกครั้ง แต่ `eval_retrieval` ตัวเดิม
ส่งคำถามดิบเข้าไปตรง ๆ ตัวเลขที่รายงานจึงต่ำกว่าที่ระบบจริงทำได้
แก้แล้วที่ `evaluation/eval_retrieval.py:74-76`

บั๊กอีกตัวในไฟล์เดียวกัน `all_misses` ถูกเขียนทับทุกรอบ เหลือแค่คอนฟิกสุดท้าย
จึงเทียบข้อที่ค้นไม่เจอข้ามคอนฟิกไม่ได้

ทั้งสองตัวมีลายเซ็นเดียวกัน — ผลที่ออกมาดูสมเหตุสมผล จึงไม่มีใครสงสัย
วิธีจับคือเดินเส้นทางของตัววัดคู่กับเส้นทางจริง แล้วตรวจว่าผ่านขั้นเดียวกันครบไหม

## 3. ขั้นที่ล้มเหลวทุกครั้ง แต่รายงานตัวเลขที่ดูปกติ

สิ่งที่ commit ไว้ใน `outputs/eval_query_transform.json`

| คอนฟิก | MRR (paraphrase) | llm_calls | ล้มเหลว | ใช้ได้ |
|---|---|---|---|---|
| raw | 0.9482 | 0 | 0 | True |
| normalize_no_slang | 0.9482 | 0 | 0 | True |
| normalize | 0.9482 | 0 | 0 | True |

ไม่มีแถวของโหมดที่ใช้ LLM เลย — `rewrite` `multi_query` `hyde`
ทั้งสามยังวัดไม่สำเร็จ จึงไม่มีตัวเลขให้รายงาน

`QueryTransformer.transform()` ดัก exception แล้วคืนคำถามเดิมอย่างเงียบ ๆ
(`query_transform.py:147-149`) ซึ่งถูกต้องสำหรับการใช้งานจริง
ขั้นเดียวล้มไม่ควรทำให้ทั้งระบบล่ม

แต่ตอนวัดผลมันกลายเป็นกับดัก โควตา Groq ฟรีหมด ทุกครั้งที่เรียก LLM ล้มเหลว
ตัววัดจึงวัด *คำถามที่ยังไม่ได้แปลง* 60 ครั้ง แล้วรายงานผลเป็นคะแนนของโหมดนั้น
ตัวเลขออกมาดูสมเหตุสมผล ในขณะที่ขั้นที่กำลังถูกวัดไม่ได้ทำอะไรเลย

ทางแก้คือห่อ LLM ด้วย `CountingLLM` (`evaluation/eval_query_transform.py:27`)
ที่นับ `llm_calls` กับ `llm_failures` แล้วตั้ง `usable = (failures == 0)` (บรรทัด 124-126)
แถวไหนที่ `usable = false` ห้ามเอาไปอ้างอิง

**หลักการ: ทุกขั้นที่ถอยกลับอย่างนุ่มนวลตอนใช้งานจริง ต้องส่งเสียงดังตอนวัดผล
ไม่งั้นจะได้ตัวเลขของสิ่งที่ไม่เคยทำงาน**

## 4. ข้อจำกัดที่แก้ด้วยโค้ดไม่ได้

คลังกับคำถามทดสอบเขียนโดยคนเดียวกัน ซึ่งย่อมตั้งคำถามด้วยกรอบความคิดเดียวกับตอนเขียนคำตอบ
ตัวเลขทุกตัวที่นี่จึงเป็นขอบบน ไม่ใช่สิ่งที่ผู้ใช้จริงควรคาดหวัง
ทางแก้คือให้คนอื่นเป็นคนเขียนคำถามทดสอบ ซึ่งยังไม่ได้ทำ

คำถามทดสอบ 60 ข้อกับคลัง 194 คู่ แปลว่าความต่าง 1-2 ข้อยังอยู่ในระดับที่บังเอิญได้
ต้องอ่านค่านัยสำคัญประกอบเสมอ

| การเปรียบเทียบ | สถิติรายข้อ | p | อ่านได้ว่า |
|---|---|---|---|
| ผสม BM25 ทำให้แย่ลง | dense 14 : hybrid 1 | 0.0009 | สรุปได้ |
| rerank ช่วยจริง | 0 : 18 | < 0.001 | สรุปได้ |
| dense vs hybrid+rerank | 0 : 5 | 0.063 | เป็นแนวโน้มเท่านั้น |

สถิติที่มีประโยชน์คือ **จำนวนข้อที่พลิก** ไม่ใช่ค่าเฉลี่ย
ตอนขยายคลังจาก 172 เป็น 194 คู่ ค่าเฉลี่ยแทบไม่ขยับ — ข้อที่ผิดเพิ่มจาก 3 เป็น 4 —
ขณะที่จำนวนคำถามที่พลิกระหว่างคอนฟิกกว้างขึ้น และ p ดีขึ้นสิบเท่า
