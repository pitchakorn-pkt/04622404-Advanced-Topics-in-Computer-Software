# LAB04 — RAG System Development I

ระบบ RAG ภาษาไทยสำหรับคำถามด้านไมโครคอนโทรลเลอร์ IoT และระบบสมองกลฝังตัว
ต่อยอดจากโครงของใบงาน DL-04 โดยเปลี่ยนโดเมนข้อมูล และปรับส่วนที่จัดการภาษาไทยด้วยการวัดผลจริง

| File | |
|---|---|
| source code | `src/` `labs/` `evaluation/` `config.py` `build_index.py` `main.py` |
| dataset | `data/iot_qa.txt` — เขียนขึ้นเองสำหรับงานนี้ 191 คู่ถาม-ตอบ |
| | `data/eval_paraphrases.txt` — คำถามสำหรับวัดผล เขียนขึ้นเอง 60 ข้อ |

---

## โจทย์ของงานนี้

ใบงานให้เปลี่ยน dataset เป็นโดเมนอะไรก็ได้ ประเด็นที่ต้องตัดสินใจคือ
**จะทำเป็นภาษาอังกฤษซึ่งเครื่องมือพร้อมกว่า หรือจะยืนยันทำภาษาไทย**

งานนี้เลือกทำภาษาไทย แต่ไม่ได้เลือกด้วยความรู้สึก — เลือกแล้ววัด
คำถามที่ตั้งไว้คือ *"ภาษาไทยแย่กว่าจริงหรือ หรือเราแค่ยังไม่ได้ตั้งค่าให้ถูก"*

คำตอบสั้น ๆ จากตัวเลขในเอกสารนี้

| | ผลลัพธ์ |
|---|---|
| ปรับส่วนที่จัดการภาษาไทยแล้วดีขึ้นไหม | **ดีขึ้นมาก** MRR 0.5779 → 0.8008 บนคำถามที่ถูกเขียนใหม่ |
| ตัวแปรที่สำคัญที่สุดคืออะไร | **embedding model** ไม่ใช่การตัดคำหรือการกรองคำ |
| "กรองคำไทยให้ดีขึ้น" ช่วยไหม | **ไม่ช่วย และทำให้แย่ลง 19%** — ดูหัวข้อผลที่เป็นลบ |

## ฐานความรู้

`data/iot_qa.txt` — คู่ถาม-ตอบภาษาไทย **191 คู่ 10 หมวด** (แตกเป็น 199 chunk)

```
[หมวด: บัสสื่อสารระยะสั้น]
Q: I2C ใช้สายกี่เส้น ต่อยังไง
A: I2C ใช้สายสัญญาณสองเส้นคือ SDA สำหรับข้อมูลและ SCL สำหรับสัญญาณนาฬิกา ...
```

หมวด: การเลือกบอร์ดและชิป · ขา GPIO และระดับแรงดัน · บัสสื่อสารระยะสั้น · Wi-Fi และเครือข่าย ·
MQTT และการรับส่งข้อความ · โปรโตคอลไร้สายอื่น · เซนเซอร์และการวัด · ไฟเลี้ยงและการประหยัดพลังงาน ·
เฟิร์มแวร์และเครื่องมือพัฒนา · การแก้ปัญหาและดีบัก

เลือกโดเมนนี้เพราะภาษาที่ใช้จริงในวงการ **ปนไทยกับอังกฤษตลอดเวลา** ซึ่งเป็นเงื่อนไขที่ทำให้
การค้นแบบผสมมีอะไรให้พิสูจน์ — คำอย่าง `ESP32-C5` `GPIO34` `ESP_ERR_TIMEOUT` ต้องอาศัยการจับคำตรงตัว
ส่วนคำถามอย่าง "บอร์ดดับเองตอนต่อเน็ต" ต้องอาศัยความหมาย เพราะไม่มีคำไหนตรงกับเอกสารเลย

คลังถูกออกแบบให้มี **หัวข้อที่ใกล้กันจนต้องแยกให้ออก** ไม่ใช่แค่เพิ่มจำนวน เช่น
โหมดหลับลึก/หลับตื้น/หลับของโมเด็ม · PWM ผ่าน LEDC กับ MCPWM กับ analogWrite ·
ESP32-C3/C5/C6/H2 · Thread กับ Zigbee กับ Matter

## วิธีรัน

```bash
pip install -r requirements.txt

python build_index.py       # สร้าง FAISS + BM25 (ครั้งแรกโหลดโมเดลราว 2.2 GB)
                            # ถ้าเปิด USE_RERANK จะโหลดเพิ่มอีกราว 2.2 GB ตอนรัน main.py
python main.py              # ถามตอบแบบโต้ตอบ
```

ถ้าต้องการให้ LLM เขียนคำตอบ ต้องมีคีย์ก่อน (ค่าเริ่มต้นใช้ Groq)

```bash
export GROQ_API_KEY=...
```

ไม่มีคีย์ก็ยังรันได้ — ตั้ง `USE_LLM = False` ใน `config.py` ระบบจะคืนข้อความที่ค้นเจอมาตรง ๆ

### วัดผล

```bash
python -m evaluation.build_golden_set    # สร้างชุดข้อสอบจากคลัง
python -m evaluation.eval_retrieval      # เทียบ dense / bm25 / hybrid
python -m evaluation.eval_generation     # วัดคุณภาพคำตอบ (ต้องมีคีย์)
python -m evaluation.metrics             # ตรวจสูตรตัววัดด้วยค่าที่คำนวณมือไว้
```

สวิตช์ทุกตัวอยู่ในหัวข้อที่ 1 ของ `config.py` เปิดปิดแล้ววัดใหม่ได้ทันที

## เครื่องมือวัดผล — และทำไมต้องซ่อมมันก่อน

ชุดข้อสอบถูกสร้างจากคำถามที่อยู่ในคลังเอง แล้วแตกเป็นหลายรูปแบบ

| รูปแบบ | ที่มา | สัดส่วนคำของคำถามต้นฉบับที่ยังเหลืออยู่ |
|---|---|---|
| `verbatim` | คำถามต้นฉบับ ใช้ดูเพดานบน | 1.00 |
| `natural` | คำถามเดิมเติมคำนำหน้าและคำลงท้าย | 0.98 |
| `slang` | แทนศัพท์ในเอกสารด้วยคำที่คนพิมพ์จริง เช่น `Wi-Fi` → `ไวไฟ` | 0.83 |
| `partial` | ตัดคำทั่วไปทิ้ง เหลือแต่คำเนื้อหา | 0.53 |
| `paraphrase` | **เขียนใหม่ด้วยมือ 60 ข้อ** | **0.25** |

(คอลัมน์ขวาวัดด้วยตัวตัดคำเดียวกับที่ระบบใช้จริง ค่าเฉลี่ยจาก 60 ข้อ)

**ปัญหาที่เจอ**: `verbatim` กับ `natural` แทบไม่ต่างจากคำถามต้นฉบับเลย — คำเหมือนเดิมเกือบทุกคำ
ผลคือทุกการตั้งค่าได้ `hit@10 = 1.0000` และ MRR ราว 0.98 เท่ากันหมด
เครื่องมือวัดตันเพดาน แยกไม่ออกว่าระบบค้นเก่งจริงหรือแค่จำคำได้
ถ้าเดินหน้าปรับปรุงต่อโดยไม่ซ่อมตรงนี้ ตัวเลขจะไม่ขยับไม่ว่าจะทำอะไร

**ทางแก้**: เขียนคำถามใหม่ด้วยมือ 60 ข้อใน `data/eval_paraphrases.txt` โดยเลี่ยงคำเดิมให้มากที่สุด
เหลือคำซ้ำเฉลี่ย 25% ซึ่งเป็นคำหน้าที่กับศัพท์เฉพาะที่เลี่ยงไม่ได้ เช่น `เซนเซอร์` `ขา` `ตอนไหน`

```
Q: อ่านค่า ADC ของ ESP32 แล้วไม่ตรงกับแรงดันจริง แก้ยังไง
P: เอามัลติมิเตอร์จิ้มได้ค่านึง แต่บอร์ดอ่านได้อีกค่านึง ทำไงให้ตรงกัน
```

ทุกตัวเลขที่ใช้ตัดสินใจในเอกสารนี้มาจากรูปแบบ `paraphrase` เท่านั้น
รูปแบบอื่นรายงานไว้เพื่อดูเพดานบน ไม่ได้ใช้เปรียบเทียบ

## ผลการทดลอง

วัดบนชุดข้อสอบเดียวกันทุกครั้ง 60 คำถาม รูปแบบ `paraphrase`

### ไล่ทีละชั้น

| ชั้น | dense MRR | hybrid MRR | hybrid hit@10 |
|---|---|---|---|
| ตั้งต้น — MiniLM ตามใบงาน | 0.3799 | 0.5779 | 0.8667 |
| + ปรับข้อความให้เป็นรูปมาตรฐาน + พจนานุกรมโดเมน | 0.3799 | 0.5779 | 0.8667 |
| + ตัด stopword ภาษาไทย | — | 0.4970 ↓ | 0.7333 ↓ |
| เปลี่ยนเป็น `multilingual-e5-base` | 0.6075 | 0.6536 | 0.9500 |
| เปลี่ยนเป็น `BAAI/bge-m3` | 0.7388 | 0.7511 | 0.9333 |
| **+ จัดอันดับใหม่ด้วย cross-encoder** | — | **0.8008** | **0.9833** |

ชั้นที่สองไม่ได้ทำให้ตัวเลขขยับ แต่เก็บไว้เพราะแก้ความผิดพลาดที่มีอยู่จริงในการตัดคำ
(ดูตารางเปรียบเทียบด้านล่าง) และเป็นเกราะกันข้อมูลที่รูปแบบไม่ตรงกันในอนาคต

### เทียบวิธีค้นหาบนระบบที่ตั้งค่าเสร็จแล้ว

| วิธี | hit@1 | hit@10 | MRR | nDCG@3 | เวลา/คำถาม |
|---|---|---|---|---|---|
| dense อย่างเดียว | 0.6167 | 0.9167 | 0.7388 | 0.7466 | 23.1 ms |
| BM25 อย่างเดียว | 0.5000 | 0.8500 | 0.6059 | 0.5992 | 0.2 ms |
| hybrid (RRF) | 0.6667 | 0.9333 | 0.7511 | 0.7335 | 20.4 ms |
| **hybrid + rerank** | **0.7000** | **0.9833** | **0.8008** | **0.7981** | 528.4 ms |

รวมทุกรูปแบบคำถาม hybrid+rerank ได้ hit@1 0.9150 · hit@10 0.9960 · MRR 0.9438 · nDCG@3 0.9305

### การจัดอันดับใหม่ด้วย cross-encoder

`BAAI/bge-reranker-v2-m3` ให้คะแนนคู่ (คำถาม, เอกสาร) พร้อมกันทีละคู่ จึงแม่นกว่าการเทียบเวกเตอร์
ที่เข้ารหัสแยกกัน วิธีใช้คือดึงผู้เข้ารอบ 20 ชิ้นจาก hybrid แล้วให้ cross-encoder เรียงใหม่เหลือ 3 ชิ้น

| | MRR | hit@10 | เวลา/คำถาม |
|---|---|---|---|
| ไม่ใช้ | 0.7511 | 0.9333 | 20.4 ms |
| ใช้ | **0.8008** | **0.9833** | 528.4 ms |

**แลกกันชัดเจน**: ช้าลง 26 เท่า และต้องโหลดโมเดลเพิ่มอีกราว 2.2 GB
งานนี้เปิดไว้เป็นค่าเริ่มต้นเพราะครึ่งวินาทีไม่มีความหมายเมื่อ LLM ใช้เวลาเขียนคำตอบเป็นวินาทีอยู่แล้ว
ปิดได้ที่ `USE_RERANK` ใน `config.py` ถ้าต้องการให้รันเบาลง หรือถ้าโหลดโมเดลไม่สำเร็จ
ระบบจะข้ามขั้นนี้เองโดยไม่ล้ม

### เทียบ embedding model

วัดด้วยชุดข้อสอบเดียวกัน dense อย่างเดียว

| โมเดล | มิติ | เพดาน token | MRR | เวลา/คำถาม | เข้ารหัสคลังทั้งก้อน |
|---|---|---|---|---|---|
| `paraphrase-multilingual-MiniLM-L12-v2` | 384 | 128 | 0.3799 | 5.9 ms | 13 s |
| `intfloat/multilingual-e5-base` | 768 | 512 | 0.6075 | 8.5 ms | 13 s |
| **`BAAI/bge-m3`** | 1024 | 8192 | **0.7388** | 22.3 ms | 224 s |

bge-m3 เข้ารหัสคลังช้ากว่า 17 เท่า แต่เป็นงานที่ทำครั้งเดียวตอนสร้าง index
ส่วนเวลาต่อคำถามต่างกันแค่ 16 มิลลิวินาที ซึ่งไม่มีความหมายเมื่อเทียบกับเวลาที่ LLM ใช้เขียนคำตอบ

**ข้อสังเกตที่ควรบันทึกไว้**: `CHUNK_SIZE = 400` ในใบงานไม่ใช่ค่าที่เลือกมาลอย ๆ
วัดแล้วพบว่า chunk ขนาด 400 ตัวอักษรของข้อความไทยกินพื้นที่สูงสุด **127 token** ขณะที่ MiniLM รับได้ 128
คือชนเพดานพอดี ค่านี้จึงเป็นเพดานของโมเดลเดิม ไม่ใช่ค่าที่เหมาะที่สุดโดยธรรมชาติ

### คุณภาพคำตอบ

วัดด้วย `llama-3.3-70b-versatile` บน Groq 20 คำถามแรกของชุดข้อสอบ รูปแบบ `paraphrase`
เปิด hybrid + rerank ปิดการจำบทสนทนาเพื่อให้แต่ละข้อเป็นอิสระ

| | ค่า |
|---|---|
| ค้นเจอเอกสารที่ถูกใน 3 ชิ้นที่ส่งให้ LLM | 0.75 |
| มีการอ้างอิงหมายเลข `[n]` ในคำตอบ | **1.00** |
| ตอบว่าไม่รู้ | 0.05 |
| คำในคำตอบที่ปรากฏในเอกสารอ้างอิงด้วย | 0.81 |
| คำในคำตอบที่ตรงกับคำตอบมาตรฐาน | 0.59 |
| เวลาเฉลี่ยต่อคำถาม | 3.18 วินาที |

สิ่งที่ตัวเลขบอก: **การบังคับให้อ้างอิงได้ผล 100%** และเมื่อค้นไม่เจอ ระบบเลือกบอกว่าข้อมูลไม่พอ
แทนที่จะเดา — ข้อ `g0023` ที่ retrieval พลาด LLM ตอบว่า *"ข้อมูลที่ให้มานั้นไม่..."* ซึ่งเป็นพฤติกรรมที่ต้องการ

> **ข้อควรระวังในการอ่านตัวเลขสองแถวล่าง**: สองค่านี้เป็นเพียงสัดส่วนคำที่ซ้ำกัน ไม่ใช่การตัดสินความถูกต้อง
> คำตอบที่เรียบเรียงใหม่ด้วยคำอื่นจะได้คะแนนต่ำทั้งที่ถูกต้อง ใช้ดูแนวโน้มว่า "ยึดตามเอกสารหรือแต่งเอง"
> ได้ แต่ใช้สรุปว่าคำตอบถูกหรือผิดไม่ได้ โครงเดิมมี prompt สำหรับให้ LLM เป็นผู้ตัดสินอยู่ใน
> `prompt_templates.py` แต่ยังไม่ได้ถูกนำมาใช้ ซึ่งเป็นสิ่งที่ควรทำต่อ

## สิ่งที่ทำแล้วไม่ได้ผล

หัวข้อนี้สำคัญพอ ๆ กับหัวข้อที่ได้ผล เพราะทั้งสามข้อคือสิ่งที่ "ควรจะช่วย" ตามสามัญสำนึก แต่วัดแล้วไม่จริง

### 1. ตัด stopword ภาษาไทยแล้วแย่ลง 19%

|  | MRR | โทเคนเฉลี่ยต่อเอกสาร |
|---|---|---|
| ไม่ตัด | **0.6136** | 90 |
| ตัดด้วยรายการของ pythainlp | 0.4970 | 50 |

เหตุผลสองข้อ หนึ่ง BM25 ลดน้ำหนักคำที่พบทุกที่ด้วย IDF อยู่แล้ว การตัดทิ้งจึงไม่ได้อะไรเพิ่ม
แต่ไปทำให้ความยาวเอกสารหายไปเกือบครึ่ง ซึ่งกระทบสูตรถ่วงความยาวของ BM25 ทั้งคลัง
สอง รายการ stopword มี 1030 คำและรวม `ทำไม` `ยังไง` `ต่างกัน` ไว้ด้วย
ซึ่งเป็นคำที่บอกว่าผู้ใช้กำลังถามอะไร ไม่ใช่คำฟุ่มเฟือย

ข้อนี้เป็นหลักฐานตรงข้ามกับสมมติฐานตั้งต้นที่ว่า "ภาษาไทยแย่เพราะกรองคำได้ไม่ดีพอ"
ปัญหาไม่ได้อยู่ที่การกรองคำ และการกรองให้หนักขึ้นทำให้แย่ลง

### 2. ปรับน้ำหนัก RRF ไม่ช่วย

| dense : bm25 | MRR |
|---|---|
| 1.0 : 0.0 | 0.7430 |
| **1.0 : 1.0 (ค่าตามใบงาน)** | **0.7517** |
| 1.0 : 2.0 | 0.7089 |
| 0.0 : 1.0 | 0.6059 |

ค่าเท่ากันดีที่สุดอยู่แล้ว ส่วนต่างที่เหลืออยู่ในระดับคำถามเดียวจาก 60 ข้อ
โค้ดยังเปิดปุ่มนี้ไว้ใน `config.py` แต่ค่าเริ่มต้นไม่เปลี่ยน

### 3. การตัด chunk ตามขอบประโยควัดไม่ออก

คลังนี้มี 191 คู่ถาม-ตอบ แตกเป็น 199 chunk แปลว่ามีเพียง 8 คู่ที่ยาวพอจะถูกตัด
และชุดข้อสอบนับ chunk ใดก็ได้ที่มาจากคู่เดียวกันว่าถูก การเปลี่ยนวิธีตัดจึงขยับตัวเลขไม่ได้เลย
จึงไม่ทำ และบันทึกเหตุผลไว้แทนที่จะทำทิ้งไว้เฉย ๆ

การกวาดค่า `CHUNK_SIZE` ให้ผลว่า 400 ดีที่สุด (0.7517) เทียบกับ 300 (0.6539) และ 500 (0.7378)
โดยค่าเกิน 500 ไม่มีความหมายเพราะข้อความยาวสุดในคลังมี 426 ตัวอักษร

## สิ่งที่แก้จากโครงเดิม

### การจัดการภาษาไทย — `src/thai_text.py` (ไฟล์ใหม่)

รวมการเตรียมข้อความไว้ที่เดียว เพื่อให้ฝั่งสร้าง index กับฝั่งค้นหาใช้ตรรกะเดียวกันเสมอ

| ปัญหา | ก่อน | หลัง |
|---|---|---|
| ชื่อรุ่นถูกยัติภังค์ฉีก | `ESP32-C5` → `['esp32','c5']` | `['esp32c5','esp32','c5']` |
| ศัพท์ทับศัพท์ถูกตัดมั่ว | `ออสซิลโลสโคป` → เศษ 8 ชิ้น | `['ออสซิลโลสโคป']` |
| ข้อความไทยรูปแบบไม่ตรงกัน | `เเปลก` ≠ `แปลก` | ปรับให้ตรงกันก่อนเสมอ |
| เลขไทย | `๓.๓` → `['๓','๓']` | `['3.3']` |

วัดแล้วพจนานุกรมของ `newmm` ตัดศัพท์ในโดเมนนี้ผิด **15 จาก 43 คำ** จึงเพิ่มพจนานุกรมเฉพาะโดเมนเข้าไป

> ข้อควรระวังสำหรับคนที่จะทำตาม: `dict_trie()` **แทนที่** พจนานุกรมหลัก ไม่ใช่รวมกับมัน
> ต้องส่ง `set(thai_words()) | set(DOMAIN_WORDS)` ไม่งั้นตัวตัดคำจะไม่รู้จักคำไทยอื่นเลยและพังหนักกว่าเดิม

### บั๊กในโครงเดิม

| ที่ | อาการ | แก้ |
|---|---|---|
| `src/generator.py` | `NoLLM` แยก prompt ด้วยคีย์ภาษาอังกฤษ `"reference data :"` แต่ prompt จริงเป็นภาษาไทย ทำให้โหมดไม่ใช้ LLM ตอบว่า "ไม่พบข้อมูล" ทุกครั้ง | ประกาศตัวคั่นไว้ที่ `prompt_templates.py` ที่เดียว แล้วให้ทั้งสองฝั่งใช้ค่าเดียวกัน |
| `evaluation/eval_retrieval.py` | `all_misses = misses` เขียนทับทุกรอบ เหลือรายงานเฉพาะการตั้งค่าสุดท้าย | เก็บสะสมแยกตามการตั้งค่า |
| `main.py` | ส่วนพิมพ์แหล่งอ้างอิงถูกคอมเมนต์ทิ้ง ทำให้ `SHOW_SOURCES` ไม่มีผล | เปิดคืน |

### อื่น ๆ

- เพิ่ม `groq` เข้า `LLM_PROVIDERS` (ปลายทางเข้ากันได้กับไลบรารี `openai` เดิม) และแจ้งชัดเจนเมื่อไม่พบคีย์
- เพิ่ม `requirements.txt` ซึ่งโครงเดิมไม่มี
- เปิดปุ่มถ่วงน้ำหนัก RRF ใน `config.py`

## ข้อจำกัดของงานนี้

- ชุดข้อสอบมี 60 ข้อ ส่วนต่างระดับ 0.01 ของ MRR คือคำถามเดียวขยับอันดับ อย่าตีความว่ามีนัยสำคัญ
- คำถามที่เขียนใหม่ 60 ข้อมาจากคนเดียว จึงมีสำนวนแบบเดียว ผู้ใช้จริงหลากหลายกว่านี้
- คำถามที่เขียนใหม่ยังเหลือคำซ้ำกับต้นฉบับเฉลี่ย 25% จึงไม่ใช่การทดสอบที่ปลอดคำร่วมโดยสมบูรณ์
  ตัวเลขที่ได้ควรถือเป็นขอบบนของความสามารถจริงเมื่อเจอคำถามที่ไม่มีคำร่วมเลย
- คลัง 191 คู่ถือว่าเล็ก ข้อสรุปเรื่องลำดับความสำคัญของแต่ละชั้นอาจเปลี่ยนเมื่อคลังใหญ่ขึ้นมาก
- ชุดข้อสอบสร้างจากคลังเดียวกับที่ใช้ค้น จึงวัดได้เฉพาะ "หาเจอไหม" ไม่ได้วัดว่าคลังครอบคลุมคำถามจริงแค่ไหน
