# LAB04 — RAG System Development I

ระบบ RAG ภาษาไทยสำหรับคำถามที่คนทั่วไปเจอเวลาใช้มือถือและคอมพิวเตอร์
ต่อยอดจากโครงของใบงาน DL-04 โดยเปลี่ยนโดเมนข้อมูล และปรับส่วนที่จัดการภาษาไทยด้วยการวัดผลจริง

| File | |
|---|---|
| source code | `src/` `labs/` `evaluation/` `config.py` `build_index.py` `main.py` |

## โจทย์ของงานนี้

ใบงานให้เปลี่ยน dataset เป็นโดเมนอะไรก็ได้ ประเด็นที่ต้องตัดสินใจคือ
**จะทำเป็นภาษาอังกฤษซึ่งเครื่องมือพร้อมกว่า หรือจะยืนยันทำภาษาไทย**

งานนี้เลือกทำภาษาไทย แต่ไม่ได้เลือกด้วยความรู้สึก — เลือกแล้ววัด
คำถามที่ตั้งไว้คือ *"ภาษาไทยแย่กว่าจริงหรือ หรือเราแค่ยังไม่ได้ตั้งค่าให้ถูก"*

คำตอบจากตัวเลขในเอกสารนี้

| | ผลลัพธ์ |
|---|---|
| ปรับส่วนที่จัดการภาษาไทยแล้วดีขึ้นไหม | **ดีขึ้นมาก** MRR 0.5454 → 0.9653 บนคำถามที่ถูกเขียนใหม่ |
| ตัวแปรที่สำคัญที่สุดคืออะไร | **embedding model** ไม่ใช่การตัดคำหรือการกรองคำ |
| "กรองคำไทยให้ดีขึ้น" ช่วยไหม | **ไม่ช่วย และทำให้แย่ลง 20%** |
| การผสม BM25 เข้ากับ dense ช่วยไหม | **ทำให้แย่ลงในคลังนี้** ต้องถ่วงน้ำหนักให้ dense นำ |
| จัดอันดับใหม่ด้วย cross-encoder ช่วยไหม | **ช่วยจริงและผ่านนัยสำคัญ** เป็นชั้นที่คุ้มที่สุด |

## ฐานความรู้

`data/daily_tech_qa.txt` — คู่ถาม-ตอบภาษาไทย **172 คู่ 10 หมวด** (แตกเป็น 172 chunk)

```
[หมวด: มิจฉาชีพและความปลอดภัย]
Q: รหัสโอทีพีบอกใครได้บ้าง
A: ไม่มีใครเลย ไม่ว่าจะอ้างเป็นธนาคาร เจ้าหน้าที่ ตำรวจ หรือฝ่ายบริการลูกค้า ...
```

หมวด: แบตเตอรี่และการชาร์จ · เครื่องช้าและพื้นที่เต็ม · อินเทอร์เน็ตและไวไฟ · บัญชีและรหัสผ่าน ·
มิจฉาชีพและความปลอดภัย · ข้อมูลและการสำรอง · แอปและการอัปเดต · หน้าจอ เสียง และกล้อง ·
การเลือกซื้อและดูแลเครื่อง · การใช้งานเอกสารและงานทั่วไป

เลือกโดเมนนี้ด้วยเหตุผลสองข้อ หนึ่งเป็นเรื่องที่คนทั่วไปถามกันจริงทุกวัน
สองคำตอบเป็นคำแนะนำเชิงวิธีการ ไม่ใช่ตัวเลขสเปกที่ตรวจสอบยากและผิดได้ง่าย
ซึ่งสำคัญเพราะคลังที่มีข้อเท็จจริงผิดจะทำให้ทั้งระบบตอบผิดโดยที่ตัววัดยังบอกว่าค้นเจอถูก

คลังถูกออกแบบให้มี **หัวข้อที่ใกล้กันจนต้องแยกให้ออก** ไม่ใช่แค่เพิ่มจำนวน เช่น
เครื่องช้าเพราะพื้นที่เต็ม กับ เครื่องช้าเพราะโปรแกรมเริ่มต้นเยอะ กับ เครื่องช้าหลังอัปเดต ·
การซิงก์ กับ การสำรองข้อมูล · ล้างแคช กับ ล้างข้อมูลแอป กับ ล้างเครื่อง

## วิธีรัน

```bash
pip install -r requirements.txt

python build_index.py       # สร้าง FAISS + BM25 (ครั้งแรกโหลดโมเดลราว 2.2 GB)
                            # ค่าเริ่มต้นเปิด rerank จะโหลดเพิ่มอีกราว 2.2 GB ตอนรัน main.py
python main.py              # ถามตอบแบบโต้ตอบ
```

ถ้าต้องการให้ LLM เขียนคำตอบ ต้องมีคีย์ก่อน (ค่าเริ่มต้นใช้ Groq)

```bash
export GROQ_API_KEY=...
```

ไม่มีคีย์ก็ยังรันได้ — ตั้ง `USE_LLM = False` ใน `config.py` ระบบจะคืนข้อความที่ค้นเจอมาตรง ๆ

### วัดผล

```bash
python -m evaluation.build_golden_set      # สร้างชุดข้อสอบจากคลัง
python -m evaluation.eval_retrieval        # เทียบ dense / bm25 / hybrid / +rerank
python -m evaluation.eval_query_transform  # เทียบขั้นปรับคำถาม (โหมด LLM ต้องมีคีย์)
python -m evaluation.eval_generation       # วัดคุณภาพคำตอบ (ต้องมีคีย์)
python -m evaluation.metrics               # ตรวจสูตรตัววัดด้วยค่าที่คำนวณมือไว้
```

สวิตช์ทุกตัวอยู่ในหัวข้อที่ 1 ของ `config.py` เปิดปิดแล้ววัดใหม่ได้ทันที

## เครื่องมือวัดผล — และทำไมต้องซ่อมมันก่อน

ชุดข้อสอบถูกสร้างจากคำถามที่อยู่ในคลังเอง แล้วแตกเป็นหลายรูปแบบ

| รูปแบบ | ที่มา | สัดส่วนคำของคำถามต้นฉบับที่ยังเหลืออยู่ |
|---|---|---|
| `verbatim` | คำถามต้นฉบับ | 1.00 |
| `natural` | คำถามเดิมเติมคำนำหน้าและคำลงท้าย | 1.00 |
| `partial` | ตัดคำทั่วไปทิ้งด้วยการแยกช่องว่าง | 0.99 |
| `slang` | แทนศัพท์ในเอกสารด้วยคำที่คนพิมพ์จริง เช่น `ไวไฟ` → `wifi` | 0.86 |
| `paraphrase` | **เขียนใหม่ด้วยมือ 60 ข้อ** | **0.25** |

(คอลัมน์ขวาวัดด้วยตัวตัดคำเดียวกับที่ระบบใช้จริง ค่าเฉลี่ยจาก 60 ข้อ)

**ปัญหาที่เจอ**: สี่รูปแบบแรกแทบไม่ต่างจากคำถามต้นฉบับ ผลคือทุกการตั้งค่าได้ `1.0000` เท่ากันหมด
เครื่องมือวัดตันเพดาน แยกไม่ออกว่าระบบค้นเก่งจริงหรือแค่จำคำได้
ถ้าเดินหน้าปรับปรุงต่อโดยไม่ซ่อมตรงนี้ ตัวเลขจะไม่ขยับไม่ว่าจะทำอะไร

`partial` แย่เป็นพิเศษกับคลังนี้ เพราะมันตัดคำด้วยการแยกช่องว่าง แต่ประโยคภาษาไทยแทบไม่มีช่องว่าง
มันจึงไม่ได้ตัดอะไรเลยและเหลือ 0.99 (ในคลังที่มีศัพท์อังกฤษปนเยอะ ค่านี้จะต่ำกว่านี้มาก)

**ทางแก้**: เขียนคำถามใหม่ด้วยมือ 60 ข้อใน `data/eval_paraphrases.txt` โดยเลี่ยงคำเดิมให้มากที่สุด

```
Q: ทำไมเน็ตมือถือช้าในบางที่ทั้งที่ขึ้นเต็มขีด
P: สัญญาณขึ้นเต็มแต่โหลดอะไรก็ไม่ขึ้น เป็นเพราะอะไร
```

เหลือคำซ้ำเฉลี่ย 25% ซึ่งเป็นคำหน้าที่ที่เลี่ยงไม่ได้
**ทุกตัวเลขที่ใช้ตัดสินใจในเอกสารนี้มาจากรูปแบบ `paraphrase` เท่านั้น**

## ผลการทดลอง

วัดบนชุดข้อสอบเดียวกันทุกครั้ง 60 คำถาม รูปแบบ `paraphrase`

### เทียบวิธีค้นหาบนระบบที่ตั้งค่าเสร็จแล้ว

| วิธี | hit@1 | hit@10 | MRR | nDCG@3 | เวลา/คำถาม |
|---|---|---|---|---|---|
| dense อย่างเดียว | 0.8500 | 0.9833 | 0.8991 | 0.9004 | 22.0 ms |
| BM25 อย่างเดียว | 0.3833 | 0.6833 | 0.4927 | 0.5091 | 0.2 ms |
| hybrid (RRF) | 0.7000 | 0.9500 | 0.7595 | 0.7460 | 20.0 ms |
| **hybrid + rerank** | **0.9500** | **1.0000** | **0.9653** | **0.9605** | 486.8 ms |

รวมทุกรูปแบบคำถาม hybrid+rerank ได้ hit@1 0.9871 · hit@10 1.0000 · MRR 0.9910 · nDCG@3 0.9898

นับข้อที่ผลพลิกจริงบน hit@1 จาก 60 คำถาม พร้อมทดสอบ McNemar

| เทียบ | ฝ่ายซ้ายถูกคนเดียว | ฝ่ายขวาถูกคนเดียว | สุทธิ | McNemar |
|---|---|---|---|---|
| dense vs hybrid | 10 | 1 | **−9** | p ≈ 0.012 |
| dense vs dense+rerank | 0 | 6 | +6 | p ≈ 0.031 |
| hybrid vs hybrid+rerank | 0 | 15 | **+15** | p < 0.001 |
| dense vs hybrid+rerank | 0 | 6 | +6 | p ≈ 0.031 |

อ่านตารางนี้ได้สองเรื่องที่ยืนยันได้ทางสถิติ

1. **การผสม BM25 ทำให้แย่ลงจริงในคลังนี้** ไม่ใช่ความผันผวน คำถามที่ dense ตอบถูกอยู่แล้ว
   ถูกทำให้ผิดไป 10 ข้อ ขณะที่ได้กลับมาเพียง 1 ข้อ
2. **การจัดอันดับใหม่ด้วย cross-encoder ช่วยจริง** และช่วยมากเป็นพิเศษเมื่อการผสมทำพัง
   โดยแก้กลับมาได้ถึง 15 ข้อ

ข้อสังเกตที่ตามมา: เมื่อเปิด rerank แล้ว `dense+rerank` กับ `hybrid+rerank` ผิดเท่ากันคือ 3 ข้อจาก 60
แปลว่า **ตัวจัดอันดับใหม่กลบผลเสียของ BM25 จนการเลือกน้ำหนักไม่สำคัญอีกต่อไป**

### น้ำหนักของ RRF — ค่านี้ไม่ใช่ค่าสากล

| dense : bm25 | ไม่ rerank | + rerank |
|---|---|---|
| 1 : 0 | **0.8991** | **0.9653** |
| 1 : 0.25 | 0.7634 | 0.9653 |
| **1 : 0.5 (ค่าที่ใช้)** | 0.7595 | **0.9653** |
| 1 : 0.75 | 0.7184 | 0.9653 |
| 1 : 1 (ค่าดั้งเดิมของสูตร) | 0.7059 | 0.9486 |
| 1 : 1.5 | 0.6524 | 0.7750 |
| 0 : 1 | 0.4927 | 0.7750 |

ค่าที่ตั้งไว้คือ `dense 1 : bm25 0.5` ซึ่งวัดได้เท่ากับการปิด BM25 ไปเลยเมื่อเปิด rerank
แต่ยังเก็บความสามารถจับคำตรงตัวไว้สำหรับคำถามที่ชุดข้อสอบนี้ไม่ครอบคลุม

**เหตุผลที่ BM25 อ่อนในคลังนี้**: คำถามกับคำตอบแทบไม่มีคำหายากที่ตรงกันเป๊ะ
เพราะเป็นภาษาไทยเชิงอธิบายล้วน ต่างจากคลังที่มีรหัสหรือชื่อรุ่นซึ่ง BM25 จะได้เปรียบ
ค่านี้จึงต้องวัดใหม่ทุกครั้งที่เปลี่ยนคลัง ไม่ใช่ตั้งตามค่าที่คนอื่นใช้

### เทียบ embedding model

วัดด้วยชุดข้อสอบเดียวกัน dense อย่างเดียว

| โมเดล | มิติ | เพดาน token | MRR | เวลา/คำถาม | เข้ารหัสคลังทั้งก้อน |
|---|---|---|---|---|---|
| `paraphrase-multilingual-MiniLM-L12-v2` | 384 | 128 | 0.5454 | 5.9 ms | 11 s |
| `intfloat/multilingual-e5-base` | 768 | 512 | 0.8415 | 8.5 ms | 12 s |
| **`BAAI/bge-m3`** | 1024 | 8192 | **0.8991** | 22.3 ms | 15 s |

นี่คือชั้นที่ให้ผลมากที่สุดในงานทั้งหมด — เปลี่ยนโมเดลตัวเดียว MRR ขึ้นจาก 0.5454 เป็น 0.8991
โดยเวลาต่อคำถามต่างกันเพียง 16 มิลลิวินาที ซึ่งไม่มีความหมายเมื่อเทียบกับเวลาที่ LLM ใช้เขียนคำตอบ

**ข้อสังเกตที่ควรบันทึกไว้**: `CHUNK_SIZE = 400` ในใบงานไม่ใช่ค่าที่เลือกมาลอย ๆ
วัดแล้วพบว่า chunk ขนาด 400 ตัวอักษรของข้อความไทยกินพื้นที่สูงสุด 127 token ขณะที่ MiniLM รับได้ 128
คือชนเพดานพอดี ค่านี้จึงเป็นเพดานของโมเดลเดิม ไม่ใช่ค่าที่เหมาะที่สุดโดยธรรมชาติ

### ปรับคำถามก่อนค้น

| โหมด | hit@1 | hit@10 | MRR | nDCG@3 | เวลา/คำถาม |
|---|---|---|---|---|---|
| ส่งคำถามดิบ ไม่ทำอะไร | 0.9500 | 1.0000 | 0.9653 | 0.9605 | 0.50 วิ |
| `normalize_query` ปิดตารางแทนคำ | 0.9500 | 1.0000 | 0.9653 | 0.9605 | 0.49 วิ |
| `normalize_query` เต็มรูปแบบ | 0.9500 | 1.0000 | 0.9653 | 0.9605 | 0.49 วิ |

**ไม่มีผลเลยในคลังนี้** ทั้งที่ตารางแทนคำถูกออกแบบมาให้อุดช่องว่างข้ามระบบตัวอักษรโดยตรง
(`wifi` → `ไวไฟ`, `อัพเดท` → `อัปเดต`) เหตุผลคือ `bge-m3` จับคู่คำเหล่านี้ได้เองในเชิงความหมายอยู่แล้ว
และรูปแบบ `slang` ที่ออกแบบมาทดสอบเรื่องนี้โดยเฉพาะก็ตัน `1.0000` ตั้งแต่ยังไม่ทำอะไร

ตารางแทนคำถูกเก็บไว้เพราะไม่มีต้นทุน แต่ต้องบันทึกตามตรงว่า **วัดแล้วไม่ได้อะไร**

โหมดที่ใช้ LLM (`rewrite` `multi_query` `hyde`) **ยังไม่มีตัวเลขที่เชื่อถือได้** เพราะโควตาของ Groq
ระดับฟรีไม่พอให้รันจนจบ `QueryTransformer.transform()` ดักข้อผิดพลาดแล้วคืนคำถามเดิมอย่างเงียบ ๆ
ซึ่งดีตอนใช้งานจริงแต่อันตรายตอนวัดผล เพราะได้ตัวเลขที่ดูสมเหตุสมผลทั้งที่ขั้นที่วัดไม่ได้ทำงานเลย
`eval_query_transform.py` จึงห่อตัว LLM ไว้นับการเรียกและการล้มเหลว แล้วบันทึกเป็นฟิลด์
`llm_calls` `llm_failures` `usable` — **แถวที่ `usable` เป็น false ห้ามนำไปใช้**

### คุณภาพคำตอบ

วัดด้วย `llama-3.3-70b-versatile` บน Groq 20 คำถามแรกของชุดข้อสอบ รูปแบบ `paraphrase`
เปิด hybrid + rerank ปิดการจำบทสนทนาเพื่อให้แต่ละข้อเป็นอิสระ

| | ค่า |
|---|---|
| ค้นเจอเอกสารที่ถูกใน 3 ชิ้นที่ส่งให้ LLM | 0.95 |

| ตอบว่าไม่รู้ | 0.00 |
| คำในคำตอบที่ปรากฏในเอกสารอ้างอิงด้วย | 0.82 |

การบังคับให้อ้างอิงได้ผลทุกข้อ และไม่มีข้อไหนที่ระบบตอบว่าไม่รู้ ซึ่งสอดคล้องกับอัตราค้นเจอ 0.95

> **ข้อควรระวังในการอ่านตัวเลขสองแถวล่าง**: สองค่านี้เป็นเพียงสัดส่วนคำที่ซ้ำกัน ไม่ใช่การตัดสินความถูกต้อง
> คำตอบที่เรียบเรียงใหม่ด้วยคำอื่นจะได้คะแนนต่ำทั้งที่ถูกต้อง ใช้ดูแนวโน้มว่า "ยึดตามเอกสารหรือแต่งเอง"
> ได้ แต่ใช้สรุปว่าคำตอบถูกหรือผิดไม่ได้ โครงเดิมมี prompt สำหรับให้ LLM เป็นผู้ตัดสินอยู่ใน
> `prompt_templates.py` แต่ยังไม่ได้ถูกนำมาใช้ ซึ่งเป็นสิ่งที่ควรทำต่อ

## สิ่งที่ทำแล้วไม่ได้ผล

### 1. ตัด stopword ภาษาไทยแล้วแย่ลง 20%

|  | MRR | โทเคนเฉลี่ยต่อเอกสาร |
|---|---|---|
| ไม่ตัด | **0.4958** | 96 |
| ตัดด้วยรายการของ pythainlp | 0.3987 | 47 |

เหตุผลสองข้อ หนึ่ง BM25 ลดน้ำหนักคำที่พบทุกที่ด้วย IDF อยู่แล้ว การตัดทิ้งจึงไม่ได้อะไรเพิ่ม
แต่ไปทำให้ความยาวเอกสารหายไปครึ่งหนึ่ง ซึ่งกระทบสูตรถ่วงความยาวของ BM25 ทั้งคลัง
สอง รายการ stopword มี 1030 คำและรวม `ทำไม` `ยังไง` `ต่างกัน` ไว้ด้วย
ซึ่งเป็นคำที่บอกว่าผู้ใช้กำลังถามอะไร ไม่ใช่คำฟุ่มเฟือย

ข้อนี้เป็นหลักฐานตรงข้ามกับสมมติฐานตั้งต้นที่ว่า "ภาษาไทยแย่เพราะกรองคำได้ไม่ดีพอ"
ปัญหาไม่ได้อยู่ที่การกรองคำ และการกรองให้หนักขึ้นทำให้แย่ลง

> การทดลองเดียวกันนี้เคยรันกับคลังคนละโดเมนมาก่อนแล้วได้ผลถอย 19% ใกล้เคียงกัน
> จึงไม่ใช่ลักษณะเฉพาะของคลังใดคลังหนึ่ง

### 2. ปรับข้อความให้เป็นรูปมาตรฐานและพจนานุกรมโดเมนไม่ขยับตัวเลข

| ขั้นตอนของตัวตัดคำ | MRR |
|---|---|
| ของใบงาน | 0.4958 |
| + ปรับรูปข้อความ | 0.4958 |
| + รวมคำที่มียัติภังค์ | 0.4958 |
| + พจนานุกรมโดเมน | 0.4927 |

เก็บไว้เพราะแก้ความผิดพลาดที่มีอยู่จริงในการตัดคำ (`พาวเวอร์แบงก์` เคยถูกฉีกเป็น 2 ชิ้น
`เอสเอสดี` เป็น 3 ชิ้น) และเป็นเกราะกันข้อมูลที่รูปแบบไม่ตรงกัน แต่ต้องรายงานตามตรงว่า
**บนคลังนี้ไม่ได้ทำให้ตัวเลขดีขึ้น**

### 3. การตัด chunk ตามขอบประโยควัดไม่ออก

คลังนี้มี 172 คู่ถาม-ตอบ แตกเป็น 172 chunk พอดี แปลว่าไม่มีคำตอบใดยาวพอจะถูกตัดเลย
การเปลี่ยนวิธีตัดจึงขยับตัวเลขไม่ได้ จึงไม่ทำ และบันทึกเหตุผลไว้แทนที่จะทำทิ้งไว้เฉย ๆ

## สิ่งที่แก้จากโครงเดิม

### การจัดการภาษาไทย — `src/thai_text.py` (ไฟล์ใหม่)

รวมการเตรียมข้อความไว้ที่เดียว เพื่อให้ฝั่งสร้าง index กับฝั่งค้นหาใช้ตรรกะเดียวกันเสมอ

| ปัญหา | ก่อน | หลัง |
|---|---|---|
| ศัพท์ทับศัพท์ถูกตัดมั่ว | `เอสเอสดี` → `['เอส','เอ','สดี']` | `['เอสเอสดี']` |
| | `พาวเวอร์แบงก์` → `['พาวเวอร์','แบงก์']` | `['พาวเวอร์แบงก์']` |
| ข้อความไทยรูปแบบไม่ตรงกัน | `เเปลก` ≠ `แปลก` | ปรับให้ตรงกันก่อนเสมอ |
| เลขไทย | `๓.๓` → `['๓','๓']` | `['3.3']` |
| ชื่อที่มียัติภังค์ | `Wi-Fi` → `['wi','fi']` | `['wifi','wi','fi']` |

วัดแล้วพจนานุกรมของ `newmm` ตัดศัพท์ในโดเมนนี้ผิด **9 จาก 40 คำ** จึงเพิ่มพจนานุกรมเฉพาะโดเมนเข้าไป

> ข้อควรระวังสำหรับคนที่จะทำตาม: `dict_trie()` **แทนที่** พจนานุกรมหลัก ไม่ใช่รวมกับมัน
> ต้องส่ง `set(thai_words()) | set(DOMAIN_WORDS)` ไม่งั้นตัวตัดคำจะไม่รู้จักคำไทยอื่นเลยและพังหนักกว่าเดิม

### บั๊กในโครงเดิม

| ที่ | อาการ | แก้ |
|---|---|---|
| `src/generator.py` | `NoLLM` แยก prompt ด้วยคีย์ภาษาอังกฤษ `"reference data :"` แต่ prompt จริงเป็นภาษาไทย ทำให้โหมดไม่ใช้ LLM ตอบว่า "ไม่พบข้อมูล" ทุกครั้ง | ประกาศตัวคั่นไว้ที่ `prompt_templates.py` ที่เดียว แล้วให้ทั้งสองฝั่งใช้ค่าเดียวกัน |
| `evaluation/eval_retrieval.py` | `all_misses = misses` เขียนทับทุกรอบ เหลือรายงานเฉพาะการตั้งค่าสุดท้าย | เก็บสะสมแยกตามการตั้งค่า |
| `evaluation/eval_retrieval.py` | เรียกตัวค้นหาโดยตรง ข้ามขั้นปรับคำถามที่ `main.py` ใช้จริง จึงรายงานตัวเลขต่ำกว่าระบบจริง | ให้ผ่าน `normalize_query` เหมือนกัน |
| `main.py` | ส่วนพิมพ์แหล่งอ้างอิงถูกคอมเมนต์ทิ้ง ทำให้ `SHOW_SOURCES` ไม่มีผล | เปิดคืน |
| `src/index_meta.py` | เทียบไฟล์ต้นทางด้วยเวลาแก้ไขล่าสุด ซึ่ง git ตั้งใหม่ตอน checkout ทำให้ clone ใหม่ถูกเตือนว่า index ล้าสมัยทุกครั้งทั้งที่ไฟล์เหมือนเดิม | เทียบด้วย SHA-256 ของเนื้อหาแทน |

### อื่น ๆ

- เพิ่ม `groq` เข้า `LLM_PROVIDERS` (ปลายทางเข้ากันได้กับไลบรารี `openai` เดิม) และแจ้งชัดเจนเมื่อไม่พบคีย์
- เพิ่ม `requirements.txt` ซึ่งโครงเดิมไม่มี
- เพิ่มปุ่มถ่วงน้ำหนัก RRF ใน `config.py` ซึ่งกลายเป็นตัวชี้ขาดในคลังนี้
- เพิ่ม `evaluation/eval_query_transform.py` สำหรับวัดขั้นปรับคำถามซึ่งเดิมไม่มีใครวัด

## ข้อจำกัดของงานนี้

- ชุดข้อสอบมี 60 ข้อ ข้อสรุปที่ผ่านนัยสำคัญมีเฉพาะสองข้อที่ระบุไว้ ส่วนต่างอื่นไม่ควรตีความว่ามีความหมาย
- **การตั้งค่าที่ดีที่สุดเหลือผิดเพียง 3 ข้อจาก 60** ทำให้แทบไม่มีที่ว่างให้วัดว่าอะไรดีขึ้นได้อีก
  ข้อสรุปที่ว่า "ตารางแทนคำไม่ช่วย" จึงอาจเป็นเพราะไม่มีที่ให้ช่วย ไม่ใช่เพราะมันไม่มีประโยชน์
- คำถามที่เขียนใหม่ 60 ข้อและคลังทั้งหมดมาจากคนเดียวกัน ผู้เขียนจึงรู้ว่าคำตอบอยู่ที่ไหน
  ตัวเลขที่ได้ควรถือเป็นขอบบน ผู้ใช้จริงที่ไม่เคยเห็นคลังจะได้ผลแย่กว่านี้
- คำถามที่เขียนใหม่ยังเหลือคำซ้ำกับต้นฉบับเฉลี่ย 25% จึงไม่ใช่การทดสอบที่ปลอดคำร่วมโดยสมบูรณ์
- ชุดข้อสอบสร้างจากคลังเดียวกับที่ใช้ค้น จึงวัดได้เฉพาะ "หาเจอไหม" ไม่ได้วัดว่าคลังครอบคลุมคำถามจริงแค่ไหน
- โหมดปรับคำถามที่ใช้ LLM ทั้งสามแบบยังไม่มีตัวเลข เพราะโควตาไม่พอ
